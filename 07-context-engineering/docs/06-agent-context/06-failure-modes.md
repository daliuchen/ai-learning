# 上下文相关的 Agent 失败模式

> Agent 跑着跑着突然变笨、原地绕圈、死守一个错误答案，原因往往既不在模型也不在 prompt，而在上下文：被错误信息污染了，被无关内容带偏了，或者装进了互相矛盾的说法。这篇把几类常见的失败模式摆出来，方便对症诊断和恢复。

---

## 1. 几类核心上下文失败

Drew Breunig 2025 年的文章《How Long Contexts Fail》把上下文失败分成四类：Poisoning、Distraction、Confusion、Clash，这套名字后来被广泛引用。下表按这四类整理，另外把 context rot 单列一行：

| 失败模式 | 含义 | 怎么认出来 |
|----------|------|-----------|
| Context Poisoning（中毒） | 错误信息（幻觉、错误工具结果）进了上下文，此后一直被当真，反复误导 | 模型坚持一个错事实，怎么纠正都绕回去 |
| Context Distraction（分心） | 上下文太长、堆满旧轨迹和无关内容，模型过度依赖上下文里的历史，被带离当前目标 | Agent 跑题、重复过去的动作、忘了在干什么 |
| Context Confusion（混淆） | 多余的内容（用不到的工具定义、无关文档）被模型拿来用 | 调了不该调的工具，答案里混进无关信息 |
| Context Clash（冲突） | 上下文里同时存在互相矛盾的信息 | 模型在两个说法间反复横跳、自相矛盾 |
| 长窗口退化（context rot） | 窗口过长，整体注意力摊薄、召回变差 | 步数越多越笨 |

这几类经常连在一起出现。一个错误的工具结果（poisoning），加上越积越长的轨迹（distraction），再加上一次纠正带进来的新说法（clash），叠在一起就是一个彻底跑飞的 Agent。

---

## 2. Context Poisoning：错误进了上下文就甩不掉

这是最危险的一类。某一步产生了错误信息，可能是模型幻觉，可能是工具返回了错数据，也可能是抓到了一个过期网页。这条内容留在上下文里，之后的每一步都会把它当成既定事实。

```
step 3: 工具返回 "pydantic 最新版是 1.10"（其实早过时了）
step 4~20: 模型基于 "1.10" 做了一连串决策、写了不兼容的代码
         你纠正它，它道歉，但上下文里 "1.10" 还在，下一步又用回去
```

症状是纠正无效，模型像记忆固化了一样，一次次回到错误结论。

对策上，靠再说一遍正确答案是压不住的。要么把污染源从上下文里清掉（删掉那条错误的工具结果，或者截断到污染发生之前），要么把子任务隔离后重跑（见[上下文隔离](./04-isolation.md)）。工具结果要能定位、要带句柄，一个原因就在这里：出了错能精确移除。

---

## 3. Context Distraction：被噪声带偏

窗口里塞了太多无关或过期的内容，最常见的是累积下来的工具结果和早已无关的旧轨迹。模型的注意力被分散，开始关注不该关注的东西，甚至忘了最初的目标。

```
# ❌ 一条上下文里堆了 40 步的全部 grep 结果、网页全文、试错日志
# 模型在第 41 步被第 12 步的某个无关片段勾走，跑去做一件不相干的事

# ✅ 对策：主动裁剪 + state 外置 + 工具结果落盘
#   - 旧的、已用完的工具结果摘要化或移除（见本章 02 篇）
#   - 把目标、待办放外部 state，每步只注入"当前焦点"（见本章 05 篇）
```

症状是跑题、被旧内容勾走、目标慢慢漂移。对策是从源头减少累积（见[Agent 的上下文累积问题](./01-accumulation.md)和[工具结果的上下文管理](./02-tool-results.md)），窗口变长后再压缩历史（见[压缩那一章](../05-compaction/01-why-compact.md)）。

---

## 4. Context Clash：矛盾信息打架

上下文里同时存在互相矛盾的内容，比如检索注入了两份说法不一致的文档，或者纠正之后新旧两个答案都还留在窗口里。模型不知道该信哪个，就在两边来回摇摆，或者胡乱拼在一起。

症状是自相矛盾，答案在两个版本之间摇摆，或者把矛盾的两边硬拼成一个答案。

对策有三条。注入前先去重、取舍，保留更可信、更新的来源，剔除与之矛盾的旧内容。纠正时用新说法替换掉旧的，别在上面叠加。多源检索的结果带上时间戳和可信度，让模型有取舍的依据。

---

## 5. 工具结果错误累积与循环

还有两个经常出现的衍生故障。

工具结果的错误会累积。单次工具出错并不致命，麻烦在于 Agent 没察觉，接着基于错结果去调更多工具，错误越滚越大。对策是给工具结果做健全性校验（schema 校验、空结果检测），出异常时显式标注失败，不要悄悄塞回上下文，必要时回滚到出错之前。

另一个是循环（loop）：Agent 反复执行同一个无效动作，同样的搜索、同样会失败的调用。根因常常是上下文里「上次这么做失败了」的信号太弱，或者被噪声淹没了。对策是在 state 里记录动作历史并显式去重（见[State vs Context](./05-state-vs-context.md)），检测到重复动作就强制换策略或终止。

```python
# ✅ 用外部 state 做循环检测（不靠模型自己在长上下文里"想起来"）
def guard_against_loop(state, action_signature: str) -> bool:
    recent = state["action_history"][-5:]
    if recent.count(action_signature) >= 3:     # 同一动作近期重复 3 次
        return True   # 触发：强制换路或终止，并往上下文注入明确提示
    return False
```

## 6. 失败模式 → 症状 → 对策 速查表

| 失败模式 | 常见症状 | 诊断信号 | 对策 |
|----------|----------|----------|------|
| Context Poisoning | 坚持错误事实、纠正无效 | 错误结论可追溯到某条工具结果或幻觉 | 清除污染源（删除或截断到污染前）；隔离重启子任务 |
| Context Distraction | 跑题、目标漂移、被旧内容勾走 | 窗口过长、塞满无关历史 | 工具结果落盘 + 摘要；裁剪旧内容；目标放 state |
| Context Confusion | 调错工具、答案混进无关信息 | 窗口里有大量用不到的工具或文档 | 按需加载工具；检索后裁剪 |
| Context Clash | 自相矛盾、答案摇摆 | 上下文含互斥说法 | 注入前去重取舍；纠正时替换而不是叠加；带来源和时间戳 |
| Context Rot（窗口过长退化） | 步数越多越笨、重复动作 | 上下文逼近窗口上限 | 压缩历史（见 [为什么要压缩上下文](../05-compaction/01-why-compact.md)）；拆多 Agent 隔离 |
| 工具结果错误累积 | 基于错结果滚雪球 | 某次工具返回异常未被察觉 | 结果校验；显式标失败；回滚 |
| 循环 | 反复同一无效动作 | action 重复 | state 记动作历史 + 去重检测 + 强制换策略或终止 |

## 7. 三种恢复手段

诊断清楚以后，恢复手段就三类，按代价从轻到重排：

- 清理（trim）：移除或摘要掉被污染、无关的内容，保留有效的轨迹。适合污染源明确、损失可控的情况。
- 重置（reset）：截断到某个干净的检查点，或者带着「已确认事实」的精简摘要重开一段上下文。适合污染已经扩散、清理起来代价太高的情况。
- 隔离（isolate）：把出问题的子任务放进一块全新的独立窗口重跑，只把结论传回来（见[上下文隔离](./04-isolation.md)）。适合需要彻底切断污染传播的情况。

```
轻 ──────────────────────────────▶ 重
清理            重置            隔离重跑
(删污染源)   (截到检查点)    (全新窗口重做子任务)
```

事后补救通常比预防贵。本章前五篇讲的少累积、早隔离、多外置都是预防，这一篇是预防没做够、事故已经发生时用的诊断和急救手册。
