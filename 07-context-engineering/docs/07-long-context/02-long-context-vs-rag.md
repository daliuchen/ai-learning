# CE 07-02：有了长上下文还要不要 RAG

> 窗口都到 1M 了，能把整个知识库直接塞进去，还要不要 RAG？我的回答是看情况，而多数情况下还要。长上下文补充 RAG，替代不了它：知识库小而稳定就直接塞，大而常变就检索，效果最好的往往是两者结合，先用 RAG 粗筛，再交给长上下文精读。

---

## 1. 这个问题为什么会被问出来

RAG（检索增强生成）出现的一个主要原因，是早年的窗口太小。4K、8K 根本装不下一个知识库，只能检索出最相关的几段放进去。

现在窗口有 1M 了，自然有人会想：把 300K 的文档全塞进去让模型自己读，切块、embedding、向量库、检索这一整套工程不就都省了？

这个想法有一部分是对的，但不能一概而论。下面按维度拆开看。

---

## 2. 决策维度逐个看

### 知识库大小

- 知识库小于窗口的一半（给输出和 rot 留出余量）：可以考虑直接塞。
- 知识库远大于窗口（几百 MB、几 GB 的企业文档库）：物理上塞不下，只能用 RAG，这是最硬的约束。

### 更新频率

- 几乎不变（一份产品手册、一套法规）：直接塞，再配 prompt caching，缓存命中后又快又便宜。
- 频繁更新（每天新增文档、实时数据）：RAG 只要更新索引；长上下文每次都得重新塞，缓存也跟着失效，反而麻烦。

### 成本

每次调用都塞 300K 输入，按量计费会线性累加。RAG 只放检索出来的几 K 到几十 K，单次成本低一个数量级。

> 长上下文配上 prompt caching，能把「重复塞同一份文档」的成本压下来；「每次塞不同的大文档」就省不了。

### 延迟

长输入的 prefill 时间长，首 token 延迟高。RAG 的输入短，prefill 快，只是要多算检索那一步的耗时，通常几十到几百毫秒，比塞 300K 的 prefill 短得多。

### 准确率

- 单针检索（找一个明确的答案）：长上下文的大海捞针表现很好。
- 综合或多跳推理：长上下文会遇到 lost-in-the-middle，埋在中间的信息读不到，准确率下降。RAG 把最相关的内容放在前面，反而更稳。
- RAG 的风险在召回：检索没召回的内容，模型根本看不到。

### 可解释性 / 引用

RAG 天然带出处，答案来自哪个 chunk、哪篇文档一清二楚，可以做引用，也可以做审计。长上下文是整份塞进去，模型的话来自哪一段很难追溯，除非另外做 citation 机制。

合规、法律、医疗这类必须能追溯的场景，RAG 的可解释性是硬需求。

---

## 3. 决策表

把上面整理成一张表，按场景对照：

| 维度 | 倾向「直接长上下文」 | 倾向「RAG」 |
|------|---------------------|------------|
| 知识库大小 | 小，能塞进半个窗口内 | 大，远超窗口 |
| 更新频率 | 几乎不变 | 频繁更新 / 实时 |
| 单次成本 | 配缓存、重复用同一份 | 每次内容不同、要省钱 |
| 延迟要求 | 可接受秒级 prefill | 要低延迟 |
| 任务类型 | 单针检索、整体摘要 | 多跳、需要精准定位 |
| 准确率 | 内容短、关键信息能放头尾 | 内容长、怕 lost-in-middle |
| 可解释性 / 引用 | 不强求溯源 | 必须可引用、可审计 |
| 工程复杂度 | 想简单、不想维护向量库 | 已有检索栈、能接受复杂度 |

> 经验上：小而稳，用长上下文；大、常变、要溯源或要省钱，用 RAG；介于两者之间，用混合方案。

---

## 4. 混合方案：RAG 粗筛 + 长上下文精读

两者不必二选一。我更推荐的做法，是用长窗口放宽 RAG 对精度的要求：

- 过去窗口只有 4K，RAG 只能放 top-3，对检索精度要求极高，漏掉一段就答不出来。
- 现在窗口有 1M，RAG 可以粗筛召回 top-50 甚至 top-100，把召回率拉满，剩下的精读和筛选交给长上下文模型。

这种做法可以叫 retrieve wide, read long：检索负责不漏，长上下文负责读懂，并从中挑出相关的部分。它和[检索结果的排序、裁剪、去重](../03-retrieval/04-rank-trim.md)里「注入阶段收紧」的建议并不冲突，代价是多放进来的段落也带进了噪声和干扰项（见 [Context Rot 与 Lost in the Middle](../01-foundations/03-context-rot.md)）：塞 50 段之前最好仍做一次 rerank 和去重，把最相关的放在头尾，并用自己的评测集确认放宽到多少不会掉点。

```python
# ✅ 混合：RAG 粗筛召回，长上下文精读
import anthropic

client = anthropic.Anthropic()

# 1) RAG 粗筛：召回多一点（top_k 拉大，重召回轻精度）
chunks = vector_store.search(query, top_k=50)   # 召回 50 段，约 60K token

# 2) 长上下文精读：把召回的 chunk 全塞给模型，让它自己判断相关性 + 综合作答
context = "\n\n".join(
    f"[来源 {c.doc_id} #{c.chunk_id}]\n{c.text}" for c in chunks
)
resp = client.messages.create(
    model="claude-opus-5-5",
    max_tokens=1500,
    messages=[{
        "role": "user",
        "content": (
            f"以下是检索到的资料，请只依据资料作答，并在每个结论后标注来源编号。\n\n"
            f"{context}\n\n问题：{query}"
        ),
    }],
)
```

上面给每一段都加了 `[来源 doc_id #chunk_id]` 标记，这样 RAG 的可溯源性就带进了长上下文，模型能引用出处，补上纯长上下文难以解释的短板。

## 5. 几个场景判断

| 场景 | 选型 | 理由 |
|------|------|------|
| 问答一份 50 页产品手册（基本不变） | 长上下文 + 缓存 | 小而稳，缓存命中后又快又便宜 |
| 企业 10 万篇文档客服知识库 | RAG（可粗筛 top-50 给长上下文精读） | 远超窗口，物理上只能检索 |
| 合同审查，结论必须引用条款 | RAG / 混合 | 可解释性要求高，要溯源到具体条款 |
| 分析单个超长代码仓库做重构建议 | 长上下文 | 需要全局理解，跨文件依赖塞进去更好 |
| 实时新闻问答 | RAG | 内容每天变，更新索引比重新塞再缓存省事 |
| 单篇长论文总结 | 长上下文 | 单文档、要全局综合、不需要检索 |

---

## 6. 常见坑

| 坑 | 说明 |
|----|------|
| 「窗口大了就不用 RAG 了」 | 大知识库物理上塞不下；动态数据和可解释性仍然需要 RAG |
| 图省事把全库塞进窗口 | 成本线性涨、prefill 慢，还会遇到 lost-in-the-middle |
| 混合方案里 top_k 还卡得很小 | 长窗口的用处就是放宽召回，多召回一些交给模型精读；放宽到多少要用评测集量，召回太多同样会被噪声拖累 |
| 长上下文不做溯源 | 合规场景里无法追溯是硬伤，至少给 chunk 加上来源标记 |
| 忽略缓存 | 反复用同一份长文档却不开缓存，钱白花了 |
