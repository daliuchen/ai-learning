# CE 08-03：上下文相关故障排查

> 模型出问题时，工程师的第一反应往往是改 prompt 的措辞。可生产故障的原因大多不在措辞，而在上下文：无关内容稀释了注意力，不同来源的信息互相冲突，关键指令埋在长历史中间，或者检索根本没命中。所以排查的第一步，是把模型实际收到的完整上下文 dump 出来，而不是对着模板猜。

---

## 1. 第一步：先 dump 上下文，再谈别的

大部分上下文故障，把渲染后的完整 messages 扫一遍就能定位。改任何代码之前，先把模型实际收到的内容打印出来。

```python
import json
# messages 是即将发给 API 的最终序列（不是你的模板）
with open("/tmp/dump_ctx.json", "w") as f:
    json.dump({"messages": messages, "tools": tools}, f, ensure_ascii=False, indent=2)
print(f"system 长度 {len(str(messages[0]))} 字符，共 {len(messages)} 条消息")
```

看这份 dump 时，留意四件事：

1. 关键信息（用户的约束、检索到的事实）在不在里面？
2. 如果在，它在什么位置，开头结尾还是中间？
3. 有没有互相矛盾的内容，比如新旧两次检索结果、历史里的旧事实和新事实？
4. 有没有一大段无关内容把有用的信号淹没了？

这四个问题，基本对应下面四类常见故障。

---

## 2. 症状 → 根因映射

### 2.1 答非所问 / 跑题 → context rot 或无关上下文

模型的回答和问题对不上，或者抓住上下文里某个无关细节展开。多半是窗口里噪声太多，关键信号被稀释了，也就是 context rot（详见 [Context Rot 与 Lost in the Middle](../01-foundations/03-context-rot.md)）。

自查方法：dump 里有效信息占多大比例？检索召回了 10 条，只有 1 条相关，另外 9 条就是在抢注意力。

### 2.2 前后矛盾 / 自相打架 → context clash

模型一会儿说 A，一会儿说非 A。原因通常是上下文里同时存在冲突的信息：第一轮检索说退货期 7 天，第三轮检索说 15 天，两条都还在历史里；或者压缩摘要保留了旧结论，新检索给的是新结论。

自查方法：在 dump 里搜同一个主题，看是不是有两份互相冲突的事实同时在场。

### 2.3 忽略指令 / 不守约束 → 指令被埋中间或被长历史稀释

system 里明明写了「绝不能泄露内部价格」，模型还是泄露了。常见原因有两个：一是这条指令埋在一大段 system 的中间（lost in the middle）；二是对话历史太长，把它稀释了，50 轮之后，开头那条约束的相对分量已经被冲淡。

自查方法：约束在 dump 里是否靠近头尾？历史是不是长到把它淹没了？

### 2.4 幻觉 / 编事实 → 检索没命中

模型一本正经地胡说，很多时候是因为该提供的事实**根本没进上下文**：检索 query 改写偏了，向量召回没命中，或者召回了但被 token 预算截掉了。这时模型不是爱编，是手上没有材料。

自查方法：dump 里到底有没有那条应该被引用的事实？没有的话，是检索的问题，不是模型的问题。

## 3. 症状 → 可能原因 → 对策速查表

| 症状 | 可能根因 | 排查动作 | 对策 |
|------|----------|----------|------|
| 答非所问 / 跑题 | 无关上下文稀释、context rot | dump 看有效信息占比 | 降检索 k、重排序、收紧召回阈值 |
| 前后矛盾 | context clash（冲突信息共存） | dump 搜同主题的多份事实 | 去重、保留最新、冲突时显式标注时效 |
| 忽略关键指令 | 指令埋在中间或被长历史稀释 | 看约束位置和历史长度 | 约束放头尾、压缩历史、关键约束每轮重申 |
| 幻觉 / 编事实 | 检索 miss、被截断、query 改写偏 | dump 查事实在不在 | 修 query 改写、查召回率、放宽 token 预算 |
| 工具调不对 / 不调 | 工具定义被截断或描述不清 | dump 看 tools schema 全不全 | 裁掉冗余工具、把描述写清楚、检查截断 |
| 输出格式时好时坏 | few-shot 被压缩挤掉、格式指令在中间 | 看格式示例在不在 | 固定保留格式示例、指令放尾部 |
| 多轮越聊越离谱 | 历史污染累积、错误结论被反复引用 | dump 看历史里有没有沉淀下来的错误结论 | 定期重置，或摘要时剔除错误结论 |
| 偶发性翻车（同样的输入时对时错） | 缓存前缀变动、检索结果不稳定 | 对比两次 dump 的差异 | 固定检索、稳住缓存前缀 |

---

## 4. 标准排查流程

```
故障上报
  │
  ├─ 1. dump 模型实际收到的完整 messages + tools
  │
  ├─ 2. 关键信息在不在 dump 里？
  │       ├─ 不在 → 检索/拼装问题（query 改写、召回、截断）→ 修上游
  │       └─ 在 ↓
  │
  ├─ 3. 在哪个位置？是不是埋在中间？
  │       └─ 埋中间 → 重排，关键信息挪头尾
  │
  ├─ 4. 有没有矛盾信息共存？
  │       └─ 有 → 去重 / 保留最新 / 标时效（context clash）
  │
  ├─ 5. 无关噪声占比高不高？
  │       └─ 高 → 降 k / 重排序 / 收紧阈值（context rot）
  │
  └─ 6. 以上都正常 → 才轮到改 prompt 措辞 / 换模型
```

改措辞和换模型排在最后。这两样成本高、见效慢，多数时候只治标。上下文没拼对，换成 Opus 照样出错。

---

## 5. 一个排查示例

症状：客服 Agent 偶尔把已经下线的旧政策当成现行政策回答。

```python
# 第一步：dump，在历史里搜「退货政策」
hits = [m for m in messages if "退货" in str(m.get("content", ""))]
for h in hits:
    print(h["role"], str(h["content"])[:80])
```

输出：

```
assistant 根据政策，退货期为 7 天 ...      ← 第 2 轮的旧检索结果，沉在历史里
user 现在还是 7 天吗？
assistant 退货期为 15 天（已更新）...      ← 第 6 轮的新检索结果
```

原因找到了：旧的 7 天结论留在历史里没清掉，和新的 15 天冲突（context clash 加上历史污染），模型在长历史里随机抓到了旧的那条。对策有两个：摘要历史时剔除已经被新事实推翻的旧结论，或者给带时效的检索结果显式标注「截至 X 日」，让模型有取舍的依据。问题出在上下文怎么装，prompt 一个字都不用改。

---

## 6. 排查原则

- 先 dump，再提假设。没看到模型的实际输入之前，所有判断都是猜。
- 把答非所问、前后矛盾、忽略指令、幻觉这四种症状，分别对应到 rot、clash、稀释、检索 miss 四类原因。
- 改 prompt 和换模型放到最后试。上下文没拼对，换更强的模型也一样出错。
