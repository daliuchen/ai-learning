# Few-shot 示例：用预算换确定性

> few-shot 示例是上下文里花预算换稳定输出的那一块，一般 1 到 5 个就够。它对格式、风格、边界情况的改善很明显，但也要算占用。这篇讲示例放哪、放几个，以及静态示例、微调、动态检索示例这三条路线分别适合什么场景。

---

## 1. few-shot 在上下文里的角色

few-shot 就是在提示里给几组「输入 → 期望输出」的范例，让模型照着做。它占的 token 是为了让输出更可控而主动付出的预算。

| 手段 | 怎么教模型 | 占上下文 |
|------|-----------|---------|
| zero-shot | 只给指令 | 不占 |
| few-shot | 指令加几个示例 | 占，每个示例几十到几百 token |
| 微调 | 改权重 | 不占上下文 |

示例最擅长传达那些用文字很难说清楚的要求，比如输出格式、语气风格、边界情况怎么处理。说十遍「要简洁专业」，不如直接给一个简洁专业的范例。

---

## 2. 放 system 还是 user

| 放法 | 适合 | 说明 |
|------|------|------|
| 放 system | 示例稳定、全程通用 | 作为格式规范的一部分，可以进缓存 |
| 放 user（多条 user/assistant 交替） | 模拟真实的多轮对话、示例随 query 变化 | 更贴近对话格式 |

```python
# ✅ 稳定示例放 system，吃满 prompt caching
SYSTEM = """你是情感分类器，输出 positive/negative/neutral 之一。

示例：
输入：这手机续航太顶了 → positive
输入：客服半天不回，差评 → negative
输入：包装一般，东西还行 → neutral"""

# 或用 messages 交替模拟（适合对话/工具调用类示例）
messages = [
    {"role": "user", "content": "这手机续航太顶了"},
    {"role": "assistant", "content": "positive"},
    {"role": "user", "content": "客服半天不回，差评"},
    {"role": "assistant", "content": "negative"},
    {"role": "user", "content": "<待分类的真实输入>"},   # 真问题放最后
]
```

## 3. 给几个：通常 1 到 5 个

| 示例数 | 效果 |
|--------|------|
| 0（zero-shot） | 现在的强模型在简单任务上通常已经够用 |
| 1–5 | 性价比最高，格式和边界基本能锁住，预算也可控 |
| 10+ | 边际收益递减，占预算，可能带进互相冲突的信号，还会稀释注意力 |

先用 zero-shot 跑，效果不稳再一个一个加示例，而不是一上来就堆 10 个，加到输出稳定就停。任务越复杂、格式越特殊，需要的示例越多，但很少超过 5 个。

```text
输出格式跑歪了      → 加 1 个标准格式示例
边界 case 处理错了  → 补 1 个该 case 的示例
风格不对           → 加 1 个目标风格示例
```

## 4. 三条路线：静态示例、微调、动态检索示例

| 路线 | 占上下文 | 灵活性 | 适合 |
|------|---------|--------|------|
| 静态 few-shot | 占，固定几条 | 改提示就行 | 任务稳定，示例少 |
| 微调 | 不占 | 改一次就定型 | 同类样本很多，追求极致的一致性或低延迟 |
| 动态 few-shot（检索式） | 占，按 query 召回 | 最高 | 示例库大，不同输入需要不同的范例 |

动态 few-shot 在工程上用得很多：维护一个示例库，每来一个 query，就检索出最相似的 k 个示例放进上下文。预算不会被堆满，示例也和当前问题贴得很近。

```python
def build_dynamic_fewshot(query, example_store, k=3):
    examples = example_store.search(query, top_k=k)   # 向量检索最相似示例
    shots = "\n".join(f"输入：{e.input} → {e.output}" for e in examples)
    return f"参考示例：\n{shots}\n\n输入：{query} →"
```

> 要权衡的是缓存：静态示例的前缀稳定，可以进缓存；动态示例每次都变，相当于牺牲缓存换相关性。示例库不到几十条就用静态的，上百上千条而且彼此差异大，再用动态的。

## 5. 示例的多样性和顺序

示例不能随便挑，质量比数量重要：

| 维度 | 要点 |
|------|------|
| 多样性 | 覆盖不同类别和边界，别全是 positive，让模型以为只有一种答案 |
| 代表性 | 主示例选常见情况，不要选极端的 corner case |
| 平衡 | 分类任务里各标签的数量大致均衡，避免诱导偏置 |
| 顺序 | 模型对最后一个示例更敏感（近因效应），别把最不常见的放在末尾；分类任务别按标签排序，免得模型学到排列规律 |
| 一致性 | 所有示例的格式和风格必须和期望的输出完全一致，模型会把示例当成标准 |

```python
# ❌ 示例标签偏向 positive，顺序又按标签聚堆
shots = ["好评1→positive", "好评2→positive", "差评→negative"]

# ✅ 标签均衡 + 打散顺序
shots = ["差评→negative", "好评→positive", "中评→neutral"]
```

## 6. 常见坑

| 坑 | 后果 | 对策 |
|----|------|------|
| 一上来就堆 10 个以上示例 | 占预算，边际收益低，还稀释注意力 | 从 0 或 1 个开始，加到稳定就停 |
| 示例格式和期望输出不一致 | 模型学偏 | 示例就按期望的输出来写 |
| 标签或类别不均衡 | 输出有偏 | 各类保持均衡 |
| 动态示例还放在 system 里 | 缓存失效 | 动态的放 user |
| 示例过时，带着旧政策或旧格式 | 误导模型 | 定期检查示例库 |
