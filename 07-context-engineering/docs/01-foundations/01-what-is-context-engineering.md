# CE 01：什么是上下文工程（Context Engineering）

> Prompt Engineering 关心指令那句话怎么写，Context Engineering 关心整个上下文窗口里装什么、按什么顺序排、每部分占多少 token。应用从「一句 prompt」长成「Agent + 工具 + 检索 + 多轮历史」之后，上下文就成了影响结果最大的变量，调它比调措辞划算得多。这篇先把这个概念和它的边界讲清楚。

---

## 1. 一个直观例子：同一句话，喂不同上下文

假设 prompt 固定是这一句：

```
请回答用户的问题。
```

换三种上下文喂进去，结果差得很远：

| 上下文里装了什么 | 模型实际看到的输入 | 输出质量 |
|------------------|--------------------|----------|
| 只有用户问题 | `用户：我们公司退货政策是几天？` | 编一个「7 天」（幻觉） |
| 问题 + 检索到的政策原文 | `[政策片段：15 天无理由退货]` + 问题 | 正确答 15 天 |
| 问题 + 30 段无关 FAQ + 政策原文埋在第 18 段 | 一大坨噪声 + 问题 | 可能答错或漏看（lost in the middle） |

prompt 一个字没改，输出从幻觉变成正确，又变回出错。决定结果的是窗口里装了什么、放在哪、混了多少噪声，而不是那句指令。Context Engineering 要处理的就是这些。

---

## 2. 边界：PE 管措辞，CE 管装载

两者经常被混在一起，先把边界划清：

| 维度 | Prompt Engineering | Context Engineering |
|------|--------------------|--------------------|
| 核心问题 | 这句指令怎么写才清楚 | 窗口里装什么、什么顺序、占多少预算 |
| 操作对象 | 一段文本（指令 / few-shot） | 整个 context window 的组装策略 |
| 常见动作 | 改措辞、加 CoT、给示例 | 检索什么、保留几轮历史、压缩、裁剪、排序 |
| 关键变量 | 语言表达 | token 分配、信息密度、位置 |
| 失败长这样 | 指令有歧义，模型跑偏 | 关键信息被噪声稀释、召回不到、超窗被截断 |
| 类比 | 写好一个函数的逻辑 | 决定这个函数的入参该传什么 |

PE 优化的是文字，CE 优化的是输入的数据流。两者是上下层关系：CE 决定窗口里有哪些块，PE 决定其中的指令块怎么写。

---

## 3. 上下文窗口里到底有几块

任何一次 LLM 调用，进窗口的内容大致分这几类，CE 管的就是它们：

```
┌─────────────────────────────────────┐
│ System / 指令      ← 角色、规则、约束   │ ← PE 在这里写措辞
├─────────────────────────────────────┤
│ Tools / 工具定义   ← 可调用的函数 schema │ ← Agent 场景占用很大
├─────────────────────────────────────┤
│ Retrieved / 检索   ← RAG 拉来的文档片段  │ ← CE 决定拉什么、拉几条
├─────────────────────────────────────┤
│ History / 对话历史  ← 前面 N 轮 user/AI  │ ← CE 决定留几轮 / 怎么压
├─────────────────────────────────────┤
│ User / 当前输入    ← 这一轮的问题        │
└─────────────────────────────────────┘
         ↓ 全部拼成一个长序列喂给模型
```

这五块在抢同一份有限的 token 预算。比如给自己定 200K 的预算（现在主力模型的窗口已经到 1M，但预算要分配这件事不变），某一块塞多了，别的块就得让位。从分配的角度看上下文，是整本手册反复用到的思路，详见 [按预算分配上下文（Context Budget）](./05-context-budget.md)。

## 4. 为什么这个概念这两年火了

「Context Engineering」这个词在 2025 年年中被频繁提起（Shopify 的 Tobi Lütke、Andrej Karpathy 等人当时都公开讨论过），之后在 Agent 圈里基本成了通用术语。背后有三股推力。

### 4.1 Agent 兴起，上下文不再是一句 prompt

传统 chatbot 一问一答，上下文就那么一点。

Agent 要多轮调用工具，每一步都把工具返回的结果塞回上下文，几个回合下来，窗口里全是工具输出、中间推理和历史。这时 Agent 能不能把事做成，主要看上下文里装了什么，措辞退到了次要位置。

### 4.2 长上下文成了标配

2023 年大家还在 4K、8K 里抠 token。到 2026-11，各家官方文档给出的窗口是：

| 模型 | 上下文窗口 |
|------|-----------|
| Claude Fable / Opus / Sonnet / Haiku 5.x | 1M |
| OpenAI GPT-6 系 | 1.05M |
| Gemini 4 Argon | 1M |

窗口大了，能塞不等于该塞。塞满几十万上百万 token 又贵又慢，还会引发 context rot，也就是中间部分的内容召回变差（见 [Context Rot 与 Lost in the Middle](./03-context-rot.md)）。怎么用好这么大的窗口，成了实际要解决的问题。

### 4.3 工具调用和检索让上下文成了主变量

RAG、function calling、MCP 普及之后，上下文里大部分内容不再是人手写的 prompt，而是程序动态拼进去的：检索片段、工具结果、记忆。主体既然是程序拼的，优化重心也就从写好措辞转到了管好拼装。

## 5. 贯穿全手册的几条原则

| 原则 | 含义 | 对应章节 |
|------|------|----------|
| 上下文是有限预算 | 窗口再大也要分配，不是随便用的 | [按预算分配上下文（Context Budget）](./05-context-budget.md) |
| 最少必要上下文 | 给恰好够完成任务的最少信息，不是越多越好 | [最少必要上下文原则](./06-minimal-context.md) |
| 越长不一定越好 | 长上下文有 rot、噪声、稀释 | [Context Rot 与 Lost in the Middle](./03-context-rot.md) |
| 每个 token 都要付费，也会拖慢响应 | 成本随输入 token 线性增长，延迟也随上下文变长而增加 | [上下文的成本与延迟模型](./04-cost-latency.md) |
| 位置有讲究 | 重要信息放头尾，别埋在中间 | [Context Rot 与 Lost in the Middle](./03-context-rot.md) |

## 6. 常见误区

| 误区 | 实际情况 |
|------|------|
| 「CE 就是 PE 换了个名字」 | PE 管措辞，CE 管装载，CE 决定窗口里有哪些块，PE 决定指令块怎么写 |
| 「窗口够大就把能塞的都塞进去」 | 成本涨、延迟增、注意力被稀释，准确率反而下降 |
| 「检索召回越多越保险」 | 噪声会淹没关键片段，召回质量比数量重要 |
| 「历史全留着，上下文才连贯」 | 远期历史应该压缩或摘要，而不是原样堆着 |
| 「换个更强的模型就不用管上下文了」 | 更强的模型一样受 rot、成本、延迟约束 |
