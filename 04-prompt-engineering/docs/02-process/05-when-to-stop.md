# PE Process 05：何时停止迭代

> 通过率从 60% 到 85% 通常不难，85% 到 95% 就难了，95% 到 99% 难到往往不值得做。这篇讲三个该停下来的信号：指标收敛、投入产出倒挂、碰到模型能力上限。最后讲到了上限之后，还能从工程上怎么绕过去。

---

## 1. 常见的迭代曲线

```
通过率
  ▲
100│                            ▒▒▒▒  ← 95% 上限区，再涨极难
   │                       ▒▒▒▒
 90│                  ▒▒▒▒
   │             ▒▒▒▒
 80│        ▒▒▒▒
   │   ▒▒▒▒
 70│▒▒
   │
   └───────────────────────────────▶ 迭代轮次
       v0  v1  v2  v3  v4  v5  v6  v7  v8 ...

观察：
  v0 → v3：每轮 +5-10 个百分点（最容易的"低垂果实"）
  v3 → v6：每轮 +1-3 个百分点（开始变难）
  v6+：每轮 +0-1 个百分点，甚至倒退
```

先理解这条曲线，比抠技术细节更要紧。前几轮越改越好，容易让人以为能一路涨到 100%，但它是有上限的。

---

## 2. 三个该停的信号

### 信号 1：指标收敛
连续 3 轮迭代，总通过率都在 1 个百分点的范围内来回波动，说明已经到了当前 prompt 加模型的上限。

```
v5: 87%
v6: 88% (+1)
v7: 89% (+1)
v8: 88% (-1)
v9: 89% (+1)
→ 最近 3 轮在 88%～89% 之间来回，停
```

再调下去，往往这里涨 1 个百分点、那里掉 1 个百分点，没有净收益。

### 信号 2：ROI 倒挂
每轮迭代都能算出两个数：成本是你的工程时间加上评测的 API 调用费，收益是通过率增量，再乘上每个百分点对业务值多少。增量按最近 3 轮平均算，免得被单轮的上下波动骗了。

刚开始收益远大于成本，到某个点之后就反过来了。

```
轮次     通过率   工程时间   API 成本   通过率增量（近 3 轮平均每轮）
v3       80%      30 min     $0.5       +5 个百分点     ← ROI 大
v6       88%      1 h        $0.5       约 +2.7 个百分点 ← ROI 变小
v9       89%      2 h        $1         约 +0.3 个百分点 ← ROI 倒挂
```

### 信号 3：能力天花板
剩下的失败样本全是模型本身搞不定的，和 prompt 关系不大。

```
v8 仍失败的 12 条:
  - 8 条：模型不知道某领域知识（要 RAG / 微调，不是 PE）
  - 2 条：本身有歧义连人都判不准
  - 2 条：模型推理能力到上限（数学多步证明）

剩下的不是 prompt 能解决的。
```

---

## 3. 怎么算达标

不用等到 100% 才停，达到业务能接受的水平就可以停。

| 任务类型 | 经验上线门槛 |
|---------|-------------|
| 内部工具 / 辅助生产 | 70-80% |
| 客户面对的非关键功能 | 85-90% |
| 业务关键路径（如支付、安全） | 95%+ + 人工兜底 |
| 自动化决策（无人审） | 99%+ |

什么程度算可以接受，应该让业务方一起定，不能由工程师自己拍板。

---

## 4. 到了天花板还能做什么

prompt 和模型都到上限了，业务还要求更高，那就得改架构。

### 方案 A：换更强模型
```
Haiku 88% → Sonnet 93% → Opus 96%
```

代价是成本和延迟，值不值得看业务。

### 方案 B：自洽采样（Self-Consistency）
跑 5 次取多数票，多步推理任务上通常能多几个百分点，采样数越多边际收益越小，代价是 5 倍成本。

### 方案 C：拆分成多步
原来一个 prompt 同时做分析、决策和生成，拆成 3 个 prompt。每一步更专注，整体准确率会上去，代价是延迟和复杂度。

### 方案 D：加 RAG
如果失败的 8 条都是因为模型不知道公司内部的业务规则，就加检索，把相关规则放进上下文。

### 方案 E：加 Tool Use
如果失败的几条涉及实时数据或精确计算，就给模型一个工具，让它去调用，而不是去猜。

### 方案 F：加人工兜底
confidence 高的自动处理，低的转人工，变成人机混合的流程。

### 方案 G：微调
这是最贵的方案。只有上面都不行、数据足够（至少 1000 条）、业务又足够重要时才考虑。

我的优先级是：F（人工兜底）> C（拆分）> D/E（RAG/Tool）> B（self-consistency）> A（换模型）> G（微调）。

---

## 5. 卡住时的诊断流程

连续 3 轮迭代没有进展时，按这个流程排查：

```
[卡住]
   ↓
失败的 10 条样本是不是"同一类问题"？
   ├── 是 → 还有方向，看是哪一类
   │         - 模型本身不会 → 方案 A/G
   │         - 涉及外部知识 → 方案 D
   │         - 需要计算/查询 → 方案 E
   │         - 推理太长 → 方案 C
   │         - 信息歧义 → 改 evalset 或拒绝场景
   │
   └── 否 → 真的到上限了
              ↓
         业务接受当前指标吗？
              ├── 接受 → 上线
              └── 不接受 → 方案 F（人工兜底） + 上线
```

## 6. 停下之后：上线和监控

迭代停了，接下来是 Stage 5 上线和 Stage 6 监控反哺：

```
[停止迭代 @ 92%]
   ↓
[Stage 5] 版本化 + 灰度上线
   ↓
[Stage 6] 线上发现新失败模式
   ↓
[新一轮 Stage 4] 针对新失败 → v_{n+1}
   ↓
（持续）
```

evalset 在 Stage 6 不断扩充，prompt 迭代会随着线上新失败一轮轮继续。

---

## 7. 案例：知道何时停的好处

| 项目 | 不知道何时停 | 知道何时停 |
|------|--------------|------------|
| 客服分类器 | 调了 3 周到 94%，团队累 | 1 周到 89%，加人工兜底，整体业务效果一样 |
| 邮件生成 | 调了一个月才到 80%，上线晚了两周多 | 2 周到 70% + 提供"重生成"按钮，用户满意 |
| 代码助手 | 死磕单 prompt 一个月 | 拆 sub-agent，3 天到位 |

---

## 8. 是否该停的 checklist

```
□ 连续 3 轮通过率在 1 个百分点范围内？
□ 失败样本是不是都属于"模型不会" / "本身有歧义" / "需要外部数据"？
□ 当前指标业务方接受吗？
□ 继续调一轮的 ROI 是否还正？
□ 想得到的"低成本、可能有效"的假设都已经试过了？

5 个里 3+ 个是 → 停
```

---

## 9. 反过来：什么时候不该停

| 信号 | 含义 |
|------|------|
| 失败仍有清晰的规律 | 还有容易拿下的部分 |
| 业务关键路径没达标 | 必须继续 |
| 出现新的失败模式（线上反哺） | 进入新一轮 |
| 模型刚换 / 上下文刚扩 | 上限已变 |
| 团队一致认为还能再调 | 相信这个判断 |

---

## 10. 几种常见的心态

工程师容易陷进去的几个想法：

| 想法 | 实际情况 |
|------|------|
| "再多调一点就能 100%" | 95% → 99% 往往比 70% → 90% 难得多，有些任务根本到不了 |
| "用户会不接受 12% 失败" | 看怎么处理失败，有人工兜底就行 |

## 11. 实战 demo：迭代曲线可视化

```python
"""可视化迭代曲线，判断是否收敛"""
import json
from pathlib import Path


def load_history(results_dir: Path) -> list[dict]:
    out = []
    for f in sorted(results_dir.glob("v*.json")):
        d = json.loads(f.read_text())
        d["version"] = f.stem
        out.append(d)
    return out


def is_converged(history: list[dict], window: int = 3, threshold: float = 0.01) -> bool:
    if len(history) < window:
        return False
    recent = [h["total_pass_rate"] for h in history[-window:]]
    return max(recent) - min(recent) < threshold


def report(history: list[dict]) -> None:
    print(f"{'Version':10s} {'Pass Rate':>10s} {'Delta':>8s}")
    prev = None
    for h in history:
        rate = h["total_pass_rate"]
        delta = "" if prev is None else f"{(rate - prev) * 100:+.1f}%"
        print(f"{h['version']:10s} {rate*100:>9.1f}% {delta:>8s}")
        prev = rate
    print()
    if is_converged(history):
        print("⚠️  最近 3 轮波动 < 1%，已收敛。考虑停止迭代。")
    else:
        print("✅  仍有改进空间，可以继续。")


if __name__ == "__main__":
    import sys
    history = load_history(Path(sys.argv[1]))
    report(history)
```

把上面的代码保存为 `demos/process/05_iter_curve.py` 后运行：

```bash
python demos/process/05_iter_curve.py results/
```

输出大致如下：

```
Version    Pass Rate    Delta
v0             65.0%
v1             74.0%    +9.0%
v2             82.0%    +8.0%
v3             87.0%    +5.0%
v4             88.5%    +1.5%
v5             88.0%    -0.5%
v6             88.5%    +0.5%

⚠️  最近 3 轮波动 < 1%，已收敛。考虑停止迭代。
```

## 12. 常见坑

| 坑 | 排查 |
|----|------|
| 追求 100% 通过 | 永远到不了，也没必要 |
| 没和业务方约定可接受门槛 | 容易过度设计 |
| 把模型能力问题当成 prompt 问题 | 该换模型或加 RAG，而不是改 prompt |
| 停下之后不监控 | 上线后 evalset 不更新，等于没建 |
| 见好就收，却没做版本化 | 后续维护无从下手 |
