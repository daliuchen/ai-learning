# PE Process 01：PE 完整生命周期

> 做出一个好 prompt，要走六个阶段：澄清需求、写 baseline、建 evalset、迭代、上线、用监控数据反哺。这篇先把整条流程的骨架画出来，后面 5 篇再分别展开。

---

## 2. 六个阶段速览

| Stage | 阶段名 | 输入 | 输出 | 时长（首轮） |
|-------|--------|------|------|--------------|
| 1 | 需求澄清 | 模糊需求 | 判定标准 + 数据形态 | 30min（不含和 PM 来回沟通） |
| 2 | Baseline | 任务 + 几个样本 | prompt v0（结果大体正确） | 1-2h |
| 3 | 建 evalset | 业务理解 | 30-50 条 JSONL + 评测器 | 2-4h |
| 4 | 迭代闭环 | evalset + v0 | v_n（达标） | 1-7 天 |
| 5 | 上线 | v_n + CI | 生产版本 + 监控 | 半天 |
| 6 | 监控反哺 | 线上数据 | 新评测样本 + 改进任务 | 持续 |

> 这是第一次做一个新 prompt 的时间投入。之后再做类似任务，evalset 可以复用，整个流程会快 2 到 5 倍。

## 3. Stage 1：需求澄清，把模糊需求转成"通过/失败"

PM 或业务方给的需求通常是这样的：

> "帮我用 LLM 把客户反馈分类成 8 个类别"

重要的信息一条都没说。反馈有多长，一句话还是 5000 字？8 个类别是什么，互斥还是可以多选？同时像 A 又像 B 的样本怎么处理？输出只要类别名，还是要带置信度？分不了类的时候输出什么？性能预算是每条几毫秒、每天多少条？分错一条的代价有多大？

这些没问清就开始写 prompt，后面一定会返工。

### 做法：问 7 个固定问题

```
□ 输入规格：长度范围、格式、语言、来源
□ 输出规格：字段、类型、范围
□ 类别 / 标签：完整清单 + 互斥关系 + 兜底
□ 模糊 / 边界：怎么处理"看起来像 A 又像 B" / 空输入 / 异常
□ 错误成本：误判 A 当 B 损失多大？要不要 confidence？
□ 性能预算：QPS、p99 延迟、每月预算
□ 评测方式：人审 vs 规则 vs LLM-judge 各占多少
```

详见 [从需求到 Prompt v0](./02-from-spec-to-v0.md)。

## 4. Stage 2：Baseline，v0 不需要完美

很多人在 v0 就开始堆技法，CoT、Few-shot、XML 标签、Self-critique 一上来全用上。

我不建议这样。v0 应该尽量朴素：

```python
# v0 应该是这样:
prompt = """你是客服反馈分类师。请把以下反馈分类成 8 个类别之一:
[bug, feature_request, complaint, praise, question, billing, account, other]

只返回类别名，不要解释。

反馈: {feedback}
"""
```

不一上来就用 CoT 和 Few-shot，原因有三个。不先跑朴素版，就不知道它能做到什么程度，没有基线，也就判断不了高级技法值不值得加。每个技法都有成本：更多 token、更慢、更复杂，加之前得证明它有用。另外，朴素版本身就够用的情况并不少见。

跑一下 v0，看通过率：

- ≥ 85%：直接用，别再调
- 60-85%：进入迭代
- < 60%：多半是任务定义或模型选错了，不是 prompt 的问题

## 5. Stage 3：建 evalset，和 v0 同步进行

evalset 不用等 v0 完美了再建，两件事几乎同时做：

```
[早 9:00] 澄清需求
[早 10:00] 起草 v0 + 心里默想 5-10 个样本
[中午] v0 写完，跑这 5-10 样本看大致行为
[下午] 把这 5-10 加上更多边界，扩到 30-50，存成 evalset
[傍晚] 跑全量 evalset，拿到 v0 的"基线分"
```

这 30 到 50 条样本的来源比例大致如下：

| 来源 | 比例 |
|------|------|
| 线上真实数据采样 | 50% |
| 人工构造的 edge case | 30% |
| 反例 / 攻击样本 | 20% |

详见 [建评测集，从 5 条到 500 条](./03-build-evalset.md)。

## 6. Stage 4：迭代闭环

```
看 evalset 上失败的样本
   ↓
按失败模式分类（这一组都是长度问题、这一组都是漏字段...）
   ↓
针对**最大的失败类**提出一个假设
   "我觉得加一个明确的长度约束会解决这 5 条"
   ↓
改 prompt（一次只改一处）
   ↓
跑同一份 evalset
   ↓
比较 v_n vs v_{n-1}:
   - 总通过率
   - 上一版失败的本次过了几条
   - 上一版通过的本次挂了几条（regression！）
   ↓
判断：
   - 净正 → 接受 → v_{n+1}
   - 净负 → 回滚
   - 互有胜负 → 看哪边的失败更严重，权衡
```

**一次只改一处。** 同时改了 3 处，效果变好了，你不知道该归功于哪一处；变差了，也不知道该回滚哪一处。

详见 [迭代闭环（看失败、提假设、修改、验证）](./04-iteration-loop.md)。

## 7. Stage 5：上线，版本化加灰度

达标的 prompt 要按一个完整的 release 来交付，包括这些内容：

```
prompts/
├── feedback-classifier/
│   ├── v3.0.0/
│   │   ├── system.txt
│   │   ├── user_template.txt
│   │   ├── eval_results.json     # 评测分数留底
│   │   ├── CHANGELOG.md          # 这个版本改了什么
│   │   └── eval_set_ref.json     # 用的哪一版 evalset
│   ├── v3.1.0/
│   │   └── ...
│   └── current → v3.0.0          # 软链接指向当前生产
```

上线分四步：

1. 灰度：先给 1% 流量用新版本，同时把 trace 同步到可观测平台
2. 对比：拉出新旧两套 trace，看输出分布有没有漂移
3. 逐步放量：1% → 10% → 50% → 100%
4. 回滚：指标一旦变差，切换 `current` 软链接，秒级回退

## 8. Stage 6：监控反哺

上线以后，生产流量会暴露出 evalset 没覆盖到的失败模式：

```
[线上] 用户反馈：分类器把投诉当成 praise 处理了
   ↓
[运维] 把这条 input 抓出来
   ↓
[PE 工程师]
   1. 复现失败
   2. 加进 evalset 的 regression.jsonl
   3. 看是否是 evalset 没覆盖的类型 → 加到 happy_path
   4. 评估是否要触发新一轮 v_{n+1} 迭代
```

evalset 会一直长大。开始时 30 条，半年后可能有 300 条。

## 9. 时间预算参考

第一次做一个中等复杂度的 prompt 任务：

| 工作 | 时间 |
|------|------|
| 需求澄清 + 几轮 PM 沟通 | 0.5-1 天 |
| 数据采样 + 探索 | 0.5 天 |
| 起草 v0 + 跑通最少样本 | 0.5 天 |
| 建 evalset（30-50 条 + 评测器） | 1 天 |
| 迭代 5-10 轮 | 1-2 天 |
| 上线（版本管理 + 灰度 + 监控） | 0.5 天 |
| 合计 | 4-6 天 |

如果是类似任务、已经有 evalset 框架，可以压到 1 到 2 天。

有人说一天就能搞定的，多半没建 evalset。

## 10. 按任务类型裁剪流程

不是每个任务都要完整走 6 个阶段。

### 简单分类（10 个类别以内）
前两个阶段可以合并着快速过，evalset 基本靠规则判定就够。1 到 2 天。

### 抽取（多字段）
走完整流程，重点是 evalset 要覆盖各种字段缺失和格式异常。3 到 5 天。

### 生成（写文案 / 邮件）
主要靠 LLM-as-judge 评测，要在自由发挥和受控之间找平衡。1 到 2 周。

### Agent / 长链
evalset 里放的是完整 trajectory，而不是单步的输入输出；评测维度包括 task success 和 step-level correctness。2 到 4 周。

### 多模态
评测要请视觉方面的专家，或者用多模态 judge。3 天起。

## 11. 反例：跳过流程的代价

下面这些事故，都是"先赶紧上线"造成的：

| 事故 | 跳过的阶段 |
|------|-----------|
| 客服分类器上线后把 30% 投诉分进 praise | Stage 3 没覆盖含反讽的样本 |
| 内容审核 prompt 改完上线，把正常内容拒了 | Stage 4 没做回归，只看通过率不看 regression |
| Prompt 改坏了，团队里没人能回滚 | Stage 5 没版本化 |
| 月底成本超预算 5 倍 | Stage 1 没问性能预算 |

每一起都能对应到流程里偷懒的那一步。

## 12. 怎么启动这套流程

手上有一个待做的 prompt 任务，可以这样开始：

1. 开一份 Notion 或文档，标题写 `<feature-name> PE Spec`
2. 写下 7 个固定问题的答案（[问题清单](#3-stage-1需求澄清把模糊需求转成通过失败)）
3. 新建一个 git repo 或子目录：
   ```
   feature-name/
   ├── spec.md          ← Stage 1 输出
   ├── prompts/
   │   └── v0/
   ├── evalset/
   │   └── samples.jsonl
   ├── eval_runner.py
   └── results/
   ```
4. 进入 Stage 2 和 3（接着读对应章节）

## 13. 常见坑

| 坑 | 排查 |
|----|------|
| 跳过 Stage 1 直接写 | 做到一半发现需求没问清，前面全白做 |
| v0 就上各种高级技法 | 判断不了这些技法值不值得加 |
| 没建 evalset 就调 prompt | 永远不收敛 |
| 一次改好几处 | 分不清是哪处改动起了作用，或者惹了祸 |
| 达标了不做版本化 | 半年后哪次改坏了，没法回滚 |
| 上线后不监控 | 看不到线上漂移 |
| evalset 半年不更新 | 评测分很高，用户却在骂 |
