# EKB 01：为什么做这个项目

> 前 7 本手册讲的是每个零件是什么、怎么用。可会用零件和能交付一个系统之间，还隔着选型、拼装和生产环境这三道坎。这本手册拿一个企业知识库项目，把这三道坎从头到尾走一遍。

---

## 1. 你已经会的，和你还不会的

假设你认真读完了前 7 本：知道 embedding 怎么选、chunk 怎么切、rerank 怎么用、上下文怎么管、Pydantic AI 怎么写 Agent。这些都属于零件知识。

现在老板说「给公司做个内部知识库问答」，你多半会卡在下面这些地方：

| 卡点 | 手册讲过吗 | 真实问题 |
|------|-----------|----------|
| 该上向量库还是直接塞长上下文？ | 各讲了，但没讲怎么选 | 几千篇文档，到底要不要 Qdrant？ |
| LangChain 还是 Pydantic AI 还是裸 SDK？ | 各讲了 | 这个场景哪个最省心？ |
| chunk + embed + 检索 + 生成怎么粘成一条线？ | 零件都有 | 中间的胶水和数据流没人教 |
| 检索回来一堆不相关的怎么办？ | 提了 rerank | demo 能跑，换成真数据准确率很难看 |
| 谁能看哪些文档？ | 几乎没讲 | HR 文档不能给全员看，这是企业刚需 |

这本手册要补的，就是表格最右边那一列。

---

## 2. 三道坎

### 坎一：判断力（选型）

需求来了，该用的是最合适的技术，而不是最酷的那个。比如：
- 几千篇文档其实用不着重型向量库，pgvector 足够
- 问答 pipeline 相对固定，上 LangChain 反而是负担
- 文档以中文为主，embedding 默认用 OpenAI 未必最好

前几本手册给了零件参数，但面对具体场景怎么拍板，得有一套方法。第 03 章专门讲这个。

### 坎二：拼装能力（胶水）

单个组件都会用，把它们粘成一条能跑的数据流时，冒出来的全是没人写过的细节：
- chunk 切完，属于哪篇文档、哪个小节这些元数据怎么带下去？
- 检索回来的片段怎么放进 prompt，模型才能正确引用？
- 流式回答加结构化引用，前后端怎么配合？

第 05、06 章把这条线一段一段接起来。

### 坎三：生产环境（会在哪出事）

教程一般停在「it works!」那一刻，真实系统的工作量大多在那之后：
- 检索回来的内容不相关，准确率上不去
- 模型编答案，在企业场景里这算事故
- 答不出却硬答，比不答更糟
- 成本和延迟超标，没法上线

第 04 章（评估先行）、07 章（检索增强）、10 章（生产化）处理的就是这些问题。

## 3. 为什么选企业知识库当载体

企业知识库（内部帮助中心）是 RAG 里最常见、也最容易暴露问题的场景：

- 需求是真的：几乎每家公司都需要，员工要查制度、流程、产品文档。
- 零件全用得上：embedding、分块、检索、rerank、上下文、结构化输出，一个不落。
- 有自己的难点：权限，也就是谁能看哪些文档。这是它和 RAG demo 拉开差距的地方，教程里很少讲。
- 能量化：答得准不准、引用对不对，都能用指标衡量，不用靠感觉。

它小到一个项目能讲透，又真实到生产上的问题都会碰到。

---

## 4. 这本手册不教什么

为了把主线讲透，有几件事刻意不做：

- 不做对外客服系统。访客、坐席、转人工、会话状态机是另一套重心（重在交接逻辑），会冲淡 RAG 主线。本手册只做对内问答。
- 不追求生产级健壮。这是教学项目，目标是把每个决策讲清楚，不是扛住百万 QPS。
- 不堆框架。能自己写一层薄代码讲清楚的，就不引入重型框架制造黑盒。

边界的完整说明见[边界与非目标](../02-design/03-boundary-nongoals.md)。

## 5. 常见误区

| 误区 | 现实 |
|------|------|
| 「读完手册就能做项目了」 | 零件不等于系统，选型、拼装、生产各是一门功课 |
| 「先把功能堆全再说」 | 不做评估就加功能，你不知道系统在变好还是变坏 |
| 「RAG demo 跑通 = 能上线」 | demo 用的是干净数据，换成真数据，差距出在检索质量上 |
| 「权限最后加就行」 | 权限要在检索阶段设计，事后补会推翻数据模型 |
| 「用最新最酷的技术准没错」 | 几千篇文档上重型向量库属于过度工程 |
