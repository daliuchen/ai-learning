# EKB 02：最终成品长什么样

> 我们要做的是一个对内的企业知识库问答系统。员工带着自己的角色提问，系统只在他有权看的文档里检索，用混合检索加 rerank 找出最相关的片段，再让模型生成带引用的回答；答不出就直接说没找到，引用可以点回原文。

---

## 1. 一次完整的问答，发生了什么

先看成品的一次交互，建立整体印象。员工小王（角色 `engineer`）在问答页输入：

> 「公司的报销额度是多少？」

系统内部走了这几步：

```
1. 收到问题 + 当前用户角色 = engineer
2. Query 改写：「报销额度」→ 扩展出「报销 限额 标准 费用」等
3. 权限过滤：只在 engineer 可见的文档里检索（HR 内部薪资文档被排除）
4. 混合检索：BM25 关键词 + 向量语义，各召回 20 条
5. 融合 + Rerank：精排出最相关的 4 条片段
6. 生成：把 4 条片段 + 问题喂给模型，强制输出「答案 + 引用了哪几篇」
7. 流式返回：答案逐字蹦出，下方列出引用的文档标题（可点回原文）
```

小王看到的是：

> 答案：差旅报销单次上限 2000 元，需在出差结束后 15 个工作日内提交。
> 引用：《差旅与报销制度》第 3 节 ·《费用报销操作指南》

如果问的是「公司今年裁员计划」这种没有对应文档的问题，系统会回答：

> 抱歉，我在你有权限访问的知识库里没有找到相关信息。

它不会编一个答案出来，这是企业知识库的底线。

## 3. 让它不止是 demo 的三个特性

普通 RAG demo 和这个项目的区别主要在下面三点。

### 3.1 权限

每篇文档标注哪些角色可见。检索时先按角色过滤，所以 HR 的薪资文档对普通工程师根本不会被召回。越权文档从一开始就不进候选集，而不是召回之后再藏起来。详见权限一章（从[为什么权限是企业知识库的难点](../08-permission/01-permission-is-devil.md)开始）。

### 3.2 引用溯源

每个答案都附上引用了哪几篇文档，可以点回原文。在企业里，没有引用的答案没人敢信。这个需求也反过来决定了数据模型：chunk 必须存它属于哪篇文档，以及文档的标题和链接。详见[引用溯源](../06-basic-rag/03-citation.md)。

### 3.3 答不出就承认

检索不到相关内容时，明确说没找到，不拿模型自己的参数化知识硬编。宁可漏答，也不能答错。详见[答不出就承认](../06-basic-rag/04-say-i-dont-know.md)。

## 4. 技术栈一览

每一层为什么这么选，细节见下一篇[技术栈与选型理由](03-tech-stack-overview.md)。

| 层 | 选择 | 为什么 |
|----|------|--------|
| 向量库 | pgvector | 几千到几万 chunk，用不着重型库 |
| 检索 | 混合（BM25 + 向量）+ rerank | 解决员工口语和文档术语对不上的问题 |
| 生成框架 | Pydantic AI | 用结构化输出强制返回答案和引用 |
| Embedding | 可切换（中文优先） | 顺便给 06 手册的 embedding 选型做实例 |
| 前端 | Next.js + SSE | 流式回答 + 引用卡片 |
| 后端 | FastAPI | 和前几本 Python 手册保持一致 |

## 5. 分几步搭出来

整个系统不是一次写完的。每一步都能单独跑通，也都能量化这一步带来了多少提升：

| 阶段 | 产出 |
|------|------|
| 评估先行（04 章） | 一个能打分的测试集，之后每次改动都拿它衡量 |
| Ingest（05 章） | demo 文档入库，可以查到 chunk |
| 基础 RAG（06 章） | 端到端跑通：能问能答，带引用 |
| 检索增强（07 章） | 加 BM25、rerank、改写，准确率明显上涨 |
| 权限（08 章） | 越权文档不召回，多角色验证通过 |
| 前端（09 章） | 能在浏览器里用的问答页 |
| 生产化（10 章） | 降本、兜底、反馈闭环、上线 checklist |
