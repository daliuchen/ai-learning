# EKB 04：MVP 优先，先跑通再优化

> 混合检索、rerank、权限、流式界面，这些不必一开始就全上。先用最朴素的单路向量检索把端到端打通，拿到一个能问能答的 baseline，再根据评估指标一项项加增强。

---

## 1. 为什么先做 MVP

做 RAG 项目最常见的失败方式，是还没跑通就想把所有增强一次堆上去。结果改一处坏一处，根本不知道问题出在哪个环节。

更稳的节奏是纵切，而不是横切：

```
❌ 横切：先把「分块」做到完美，再把「检索」做到完美，再…… → 很久看不到端到端效果
✅ 纵切：先用最简单的方式打通「问 → 答」整条链 → 再逐段增强
```

先做 MVP 有几个好处。很多坑只有端到端跑起来才会出现，比如数据格式、prompt 拼接、延迟。有了一个能打分的起点，后面每项增强才能算出涨了多少。另外，手里有个能用的东西，人也更愿意继续做下去。

---

## 2. 这个项目的 MVP 砍到哪

完整系统有下面这些能力，MVP 阶段只保留最细的一条线：

| 能力 | 完整版 | MVP |
|------|--------|-----|
| 分块 | 语义分块 + 元数据 | 固定长度切，能切就行 |
| 检索 | 混合 + rerank + query 改写 | 单路向量检索，top-k |
| 生成 | 结构化输出 + 引用 + 兜底 | 先能带引用就行 |
| 权限 | 按角色过滤 | 先不做，全部可见 |
| 前端 | 流式 + 引用卡片 + 后台 | 先用命令行或脚本调 |
| 评估 | 完整测试集 | 一个小测试集（这项不能砍） |

评估不能砍。它是衡量改动的标尺，砍掉它就等于闭着眼睛改代码。其他部分都可以从最简单的版本开始。

## 3. MVP 的最小数据流

```python
# MVP 版检索 + 生成（伪代码，完整实现见 06 章）
def answer(question: str) -> Answer:
    # 1. 把问题 embed
    q_vec = embed(question)
    # 2. 单路向量检索 top-5（先不管权限、不管 BM25）
    chunks = db.query(
        "SELECT content, doc_id FROM chunks "
        "ORDER BY embedding <=> %s LIMIT 5",
        [q_vec],
    )
    # 3. 拼 prompt，让模型带引用回答
    return generate(question, chunks)
```

就这么简单。这十来行跑通之后，你手里就有了一个可以打分、可以迭代的系统。

## 4. 然后按指标加增强

有了 MVP 和测试集，之后每一步都走同一个循环，也就是 04、07 手册讲过的评测驱动迭代：

```
测当前指标 → 加一个增强 → 重测 → 涨了就留，没涨/变差就回退
```

增强一项一项地加，每加一项都用第 04 章的指标量化：

| 增强 | 预期改善 | 在哪一章 |
|------|----------|----------|
| 语义分块（替代固定切） | 召回更完整 | 05 章 |
| BM25 + 混合检索 | 专有名词、缩写的召回 | 07 章 |
| Rerank | 精排准确率 | 07 章 |
| Query 改写 | 口语问题的召回 | 07 章 |
| 权限过滤 | 安全性（不是准确率） | 08 章 |

每次只加一项，单独测量。一次加三项，涨了不知道是哪项的功劳，跌了也不知道该怪谁。这就是 [04-prompt-engineering 里「一次只改一处」](/docs/04-prompt-engineering/02-process/04-iteration-loop)的原则放到 RAG 上。

---

## 5. 常见坑

| 坑 | 后果 | 正确做法 |
|----|------|----------|
| 一次性堆所有增强 | 跑不通，也不知道哪坏了 | 先纵切打通 MVP |
| 连评估也省了 | 凭感觉改 | 评估是 MVP 里唯一不能砍的 |
| 一次改多项再测 | 涨跌都没法归因 | 一次只加一项，单独测 |
| MVP 阶段就纠结分块细节 | 迟迟看不到端到端效果 | 先固定长度切，05 章再优化 |
| baseline 没存档 | 后面无法对比 | 记下 MVP 的指标作为起点 |
