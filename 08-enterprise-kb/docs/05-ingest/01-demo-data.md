# EKB 21：准备 demo 企业文档集

> 这个项目用一份通用的企业 demo 数据，包含 HR、IT、产品三类文档，读者一看就懂，也足以体现权限边界。这篇讲这份文档集怎么设计：分几个空间、每个空间放什么、可见角色怎么标。后面所有章节都在这份数据上跑。

---

## 1. 为什么用通用 demo 数据

demo 数据没有用哪家公司的真实文档，是专门造的一份通用数据，理由有四个：

- HR 制度、IT 流程、产品手册在各行各业都有，谁都看得懂
- 权限边界是现成的，比如薪资文档只有 HR 能看
- 跟着做的人不需要真实数据，就能完整复现整个项目
- 能精确设计「答不出」「越权」这类评估用例

代价是得自己动手造。不过造一份小而精的 demo 数据，比折腾真实数据脱敏快得多。

---

## 2. 文档空间设计

文档按 `space`（空间）划分，不同空间对应不同的可见角色：

| space | 文档示例 | 可见角色（acl） |
|-------|----------|----------------|
| `hr` | 考勤制度、年假政策、报销制度 | `all`（公开制度） |
| `hr-private` | 薪资核算细则、绩效评定标准 | `hr`，按文档另加（薪资细则加 `finance`，绩效标准加 `manager`） |
| `it` | VPN 配置、设备申领、账号开通 | `all` |
| `product` | 产品功能说明、API 文档 | `all`, `engineer` |
| `product-internal` | 未发布功能规划、内部路线图 | `product`, `engineer` |

设计时要在同一类内容里分出公开和受限两档，比如 `hr` 和 `hr-private`。有了这种区分，才造得出「同一个问题，不同角色命中不同文档」的权限用例。

## 3. 一篇文档长什么样

格式用 Markdown，标题层级要清晰，语义分块会用到：

```markdown
---
title: 差旅与报销制度
space: hr
roles: [all]
source_url: https://wiki.internal/hr/travel-reimbursement
updated_at: 2026-03-01
---

# 差旅与报销制度

## 1. 适用范围
本制度适用于全体员工因公出差产生的费用报销。

## 2. 报销标准
### 2.1 交通费
高铁二等座、经济舱机票据实报销。

### 2.2 住宿费
一线城市每晚上限 600 元，其他城市 400 元。

## 3. 报销流程
### 3.1 单次额度
差旅报销单次上限 2000 元。
### 3.2 时限
需在出差结束后 15 个工作日内提交。
```

frontmatter 里的 `space`、`roles`、`source_url`、`updated_at` 会解析进 `documents` 表和 `acl` 表；正文的 `#`、`##`、`###` 标题层级则交给语义分块，用来切片并生成 `section_path`。

## 4. 数据和评估用例一起设计

数据和评估用例最好同时设计，这样才能保证关键场景都覆盖到：

```jsonl
// 直球：命中公开文档
{"question":"差旅报销单次上限多少？","expected_doc_ids":[7, 9],"asker_role":"all"}
// 口语化：测改写/混合检索
{"question":"出差花的钱多久能报？","expected_doc_ids":[7],"asker_role":"all"}
// 权限：HR 能命中私有文档
{"question":"绩效是怎么评定的？","expected_doc_ids":[15],"asker_role":"hr"}
// 越权：普通员工命中不到私有文档
{"question":"绩效是怎么评定的？","expected_doc_ids":[],"asker_role":"engineer"}
// 答不出：知识库里没有
{"question":"公司股票什么时候上市？","expected_doc_ids":[],"asker_role":"all"}
```

最后两条最重要，权限和兜底能不能验证，全靠它们。

## 5. 数据规模

教学项目不需要大量数据，能覆盖各个场景就行：

```
~20 篇文档，跨 5 个 space
切完 ~150-300 个 chunk
配 20-30 条评估用例
```

这个量足以暴露口语错配、权限、兜底这些真实问题，同时小到 ingest 几秒就完成，迭代很快。换成真实项目，把文档换成你们自己的，流程完全一样。

---

## 6. 常见坑

| 坑 | 后果 | 正确做法 |
|----|------|----------|
| 文档没有标题层级 | 语义分块没法切 | 用规范的 #/## 结构 |
| 不区分公开/受限文档 | 造不出权限用例 | 设计 hr 和 hr-private 两档 |
| 数据和评估集分开造 | 覆盖不到关键场景 | 一起设计，确保有权限和兜底用例 |
| 一上来造几百篇 | 迭代慢 | ~20 篇够用 |
| frontmatter 缺字段 | acl 和引用信息丢失 | 补全 space/roles/url/updated_at |
