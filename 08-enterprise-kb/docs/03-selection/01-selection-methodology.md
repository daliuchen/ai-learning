# EKB 11：选型方法论，先定边界再选技术

> 技术选型最常见的错误，是一上来就比 Qdrant 和 Milvus。顺序应该反过来：先回答规模多大、内容是什么形态、谁在用、多久更新一次这几个边界问题，答完之后选项往往只剩一两个。选型要找的是最匹配的方案，不是最强的。

---

## 1. 两种选型路径

```
❌ 错误：听到「做知识库」→ 立刻 Google「最好的向量数据库 2026」
        → 看到 Milvus 性能榜第一 → 选 Milvus
        → 几千篇文档用上了能扛十亿向量的库，运维成本爆炸

✅ 正确：先问「我有多少文档？切完多少 chunk？」→ 几千 chunk
        → 这个规模 pgvector 完全够 → 还能少维护一个组件
        → 选 pgvector
```

前一种是看参数和榜单选，后一种是从需求倒推。本手册走后一种。

---

## 2. 选型前先回答 5 个边界问题

任何 RAG 系统选型之前，先把下面 5 个问题答了：

| 问题 | 影响什么 | 我们的答案 |
|------|----------|-----------|
| 规模：多少文档？切完多少 chunk？ | 要不要重型向量库 | 几百到几千篇，几千到几万 chunk |
| 内容形态：FAQ？长文档？混合？ | 分块策略 | 结构化长文档（制度、手册） |
| 谁在用：内部？外部？多少并发？ | 权限、并发、SLA | 内部员工，低并发 |
| 更新频率：静态？天天改？ | 索引和增量策略 | 偶尔更新（制度改版） |
| 只问答还是要干活：问答？agentic？ | 要不要 Agent 编排 | 只做问答 |

这张表填完，大部分「该用什么」的问题就已经有答案了。

## 3. 从边界答案推出技术选择

逐条看这些答案怎样把选项砍掉。

### 规模在几千到几万 chunk：pgvector

这个量级下，向量检索就算全表扫也不慢，加上 HNSW 索引能做到毫秒级。Milvus、Qdrant 集群这类专用向量库面向的是百万级以上的向量和独立扩缩容，我们用不上。pgvector 还能和业务数据放在同一个库，做 ACL join 很方便。

### 内容是结构化长文档：语义分块

制度和手册有清晰的标题层级，按固定长度切会把小节切碎。应该按结构切，每个片段带上 section 元数据。

### 用户是内部员工、并发低：不需要重型基建

CDN、限流、多区域都不用考虑，一台机器加一个 Postgres 就够了。省下的精力花在检索质量上。

### 偶尔更新：增量重跑即可

不需要实时索引管道。哪篇文档变了，就重新 ingest 那一篇。

### 只做问答：不需要 Agent 编排

系统没有查订单、调 API 这类动作，一条固定的检索加生成 pipeline 就够了，用不上 LangGraph 或 Agent 那种动态编排。

## 4. 两条反直觉的原则

### 原则一：少一个组件，就少一份运维

每引入一个新组件（向量库、缓存、消息队列），就多一份部署、监控、排障、升级的工作。现有的 Postgres 能解决的，就不要引入新组件。小团队和教学项目尤其如此。

### 原则二：先做成可替换的，不求一步到位

拿不准的那一层，做成可替换的接口，别押注某个所谓的最优解。比如 embedding 模型，中文场景哪个最好需要实测，那就把它抽象成一个函数，随时能换。详见下一篇和[Embedding 选型](./03-embedding-selection.md)。

## 5. 一个完整的推导示例

「我要不要上 Redis 做缓存？」

```
问：当前瓶颈是什么？ → 还没上线，没有瓶颈
问：有重复查询吗？  → 有，高频问题会重复
问：Postgres 扛得住吗？ → 低并发，完全扛得住
结论：现在不上 Redis。先用 prompt caching（模型层）降本（10章），
      真出现 DB 压力再说。← 不为「将来可能」过度工程
```

每次遇到「要不要上 X」都这样推一遍，架构自然会保持精简。

---

## 6. 常见坑

| 坑 | 后果 | 正确做法 |
|----|------|----------|
| 先比技术再想需求 | 选出过度设计的方案 | 先答 5 个边界问题 |
| 追性能榜单 | 用上了用不到的能力 | 选和规模匹配的，不选最强的 |
| 为「将来可能」上组件 | 运维负担和复杂度上升 | 出现真瓶颈再上 |
| 押注一个「最优」选型 | 选错了要推翻 | 拿不准的层做成可替换 |
