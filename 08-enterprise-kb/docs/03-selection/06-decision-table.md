## 1. 完整决策表

| 决策点 | 我们的选择 | 关键理由 | 什么时候该换 |
|--------|-----------|----------|--------------|
| 向量库 | pgvector | 几千到几万 chunk，组件少，能 join ACL | 百万级以上向量、要独立扩缩容 → 评估 Qdrant/Milvus |
| Embedding | 可切换（demo 用百炼 `text-embedding-v4`，BGE、Qwen3-Embedding 等开源模型作候选） | 中文效果要实测，接口可换 | 文档不能出内网 → 本地部署开源模型 |
| 生成框架 | Pydantic AI | 用结构化输出强制引用和兜底 | 需要动态编排或多 Agent → LangGraph |
| 编排方式 | 自写薄层（直线 pipeline） | 透明、可控、能逐步评估 | 出现动态决策的信号 → 重框架 |
| 检索策略 | 混合 + rerank + 改写 | 解决口语和术语对不上的问题 | 召回已经够好时可以简化（先测） |
| 前端通信 | SSE | 服务器单向流式推送 | 需要双向实时 → WebSocket |
| 后端语言 | Python (FastAPI) | 复用 AI 生态 | — |
| 前端语言 | TypeScript (Next.js) | UI 体验、组件生态 | — |
| 生成模型 | 强模型（如 `claude-sonnet-5-5`、`gpt-6.1-sol` 这一档） | 「找不到就承认」需要很好的指令遵循 | 评估通过的更便宜模型 |
| 缓存 | prompt caching（模型层） | 降本，不需要额外组件 | 出现 DB 瓶颈再加 Redis |

## 2. 决策背后的三条原则

这些决策不是各自孤立做出来的，背后有几条一以贯之的原则。

### 原则一：匹配规模，不追最强

选 pgvector 而不是 Milvus，自写薄层而不是 LangGraph，理由都一样：这个规模和复杂度用不到那么重的东西。选型看匹配度，不看谁更强。

### 原则二：少组件，少运维

Postgres 能解决的就不引入向量库，模型层缓存够用就不上 Redis。每多一个组件，就多一份长期维护的负担。

### 原则三：拿不准的地方留可替换的接口

embedding 做成接口，模型通过 Pydantic AI 一行就能换。判断不准的地方留出弹性，别写死。

## 3. 过度设计的版本长什么样

同一个需求，常见的过度设计版本是这样的：

```
❌ 过度工程版：
Milvus 集群（8000 向量）+ LangGraph 编排（直线 pipeline）
+ 独立 rerank 服务 + Redis + Kafka 文档变更队列
+ 微服务拆 5 个 + k8s 部署

结果：组件将近十个，运维爆炸，团队 3 人，光部署就两周，
      而真实负载一台机器一个 Postgres 就能扛。
```

我们的版本是 1 个 Postgres、1 个 Python 服务、1 个前端。功能一样，要部署和维护的组件少得多。

## 4. 用到你自己的项目上

做自己的 RAG 项目时，可以照着这个流程走一遍：

```
1. 先答 5 个边界问题（规模/形态/用户/更新/是否agentic）—— EKB 11
2. 规模 < 百万向量？ → pgvector，否则评估专用库
3. 中文为主？ → 商用 API 和开源模型（BGE、Qwen3-Embedding 等）放进自己的评估集一起比
4. pipeline 是直线？ → 自写薄层 + Pydantic AI；是动态图 → 重框架
5. 每个「要不要上 X」都问「现在有这个瓶颈吗」 —— 没有就不上
6. 不确定的层 → 做成可替换接口
```

按这个流程走，一般既不会过度设计，也不会漏掉关键能力。

## 5. 常见坑

| 坑 | 后果 | 正确做法 |
|----|------|----------|
| 照抄别人的「最佳架构」 | 规模和场景不匹配 | 从自己的边界推导 |
| 每个决策单独拍板 | 整体过度设计或失衡 | 回到上面三条原则对照 |
| 一次定死所有选型 | 实测发现选错了很难改 | 拿不准的留成可替换 |
| 忽略运维成本 | 上线后维护很痛苦 | 把组件数量当硬指标来控制 |
