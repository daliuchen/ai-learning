# EKB 15：什么时候需要重框架

> 本项目的检索和 ingest 都是自己写的一层薄代码，只有生成层用了 Pydantic AI。框架用不用，看逻辑的形状：逻辑是固定 pipeline 时，自己写更透明、更好控制；需要动态编排、多 Agent、复杂状态时，重框架才值得引入。这篇给出判断标准。

---

## 1. 自写和框架在权衡什么

```
自写薄层：              重框架（LangChain/LangGraph）：
+ 每行可读、可调试        + 现成的组件、集成、最佳实践
+ 没有黑盒               + 复杂编排开箱即用
+ 依赖少                 + 社区生态
- 要自己写胶水           - 抽象层多，出问题难定位
- 没有现成集成           - 版本升级可能破坏行为
                        - 简单场景上它是负担
```

权衡的是透明可控和开箱即用。场景越简单、越固定，自己写越划算；越复杂、越动态，框架越值。

---

## 2. 判断标准：pipeline 是直线还是图

| 你的逻辑长这样 | 选择 |
|----------------|------|
| 检索 → 生成（固定直线，无分支） | 自写薄层 |
| 检索 → 判断 → 可能再检索 → 调工具 → 反思 → 再生成（动态图） | 重框架（LangGraph 等） |

本项目的 Query 流是一条直线：`rewrite → 过滤 → 检索 → rerank → 生成`，中间没有由模型决定下一步做什么的动态分支。**直线型 pipeline 自己写最清楚**，每一步是一个函数，按顺序串起来就是整个流程。

---

## 3. 本项目里哪些自写、哪些用框架

按层分工，每层单独决定：

| 层 | 选择 | 为什么 |
|----|------|--------|
| Ingest（解析、分块、入库） | 自写 | 逻辑简单固定，自写最透明 |
| 检索（向量、BM25、混合、rerank） | 自写薄层 | 每一步都要精细控制和评估，黑盒会碍事 |
| 生成（结构化输出） | Pydantic AI | 结构化输出是它的强项，自己写校验和重试不值得 |
| 前端 | Next.js + 组件库 | UI 的基础设施用现成的 |

分工的思路是：枯燥又通用的部分借脚手架，核心且需要掌控的部分自己写，有专门强项的就直接用那个库。

---

## 4. 出现哪些信号，就该上重框架了

如果将来需求变了，出现下面这些情况，就该考虑 LangGraph 这类编排框架：

- 动态决策：模型要自己决定是先检索，还是先问一个澄清问题。
- 多 Agent 协作：检索 Agent、写作 Agent、审核 Agent 之间互相传递结果。
- 复杂状态和循环：比如检索结果不满意就改写 query 再检索的反思循环。
- 中断和恢复：长任务要能暂停，等人工介入后再继续。

这些是 [01 手册 LangGraph](/docs/01-langchain/03-langgraph/01-introduction) 擅长的场景。本项目在非目标里刻意避开了它们，所以用不上。

---

## 5. 自写不等于从零造轮子

「自写薄层」常被理解成什么都自己实现，其实不是。我们照样用现成的库：

- 用 `psycopg` / `pgvector` 连数据库，不自己实现 SQL 协议
- 用 `rank-bm25` 算 BM25，不自己实现算法
- 用 `sentence-transformers` 做 embedding 和 rerank，不自己训模型
- 用 Pydantic AI 做结构化生成

自写的只是把这些库串成业务流程的那层胶水。不引入大框架替你串，免得最后看不清它是怎么串的。底层用库，控制流留在自己手里。

---

## 6. 常见坑

| 坑 | 后果 | 正确做法 |
|----|------|----------|
| 简单的直线 pipeline 上 LangGraph | 白白增加复杂度，难调试 | 自己写函数串起来 |
| 把「自写」理解成全部造轮子 | 重复实现 BM25、embedding | 底层用库，自己写胶水 |
| 怕麻烦全交给大框架 | 出问题很难定位 | 核心部分自己写 |
| 该上框架时还硬撑自写 | 动态编排代码失控 | 出现动态决策或多 Agent 的信号就上框架 |
