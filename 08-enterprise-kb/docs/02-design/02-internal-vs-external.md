# EKB 07：对内知识库与对外客服的差别

> 「给文档做个问答」听上去是一件事，实际上对应两种产品：对内的员工知识库和对外的客户客服。两者的技术重心几乎不重叠，对内最难的是权限，对外最难的是人机交接。本手册只做对内，这篇解释为什么两者不该混在一起做。

---

## 1. 一张对比表

| 维度 | 对内知识库（本手册） | 对外客服系统 |
|------|---------------------|--------------|
| 谁在问 | 内部员工（已登录、有角色） | 外部访客（匿名或弱身份） |
| 核心诉求 | 快速查到自己有权看的文档 | 解决问题，必要时找到人 |
| 最大难点 | 权限：谁能看哪些文档 | 转人工：什么时候交给坐席、怎么交回来 |
| 转人工 | 基本不需要 | 核心功能 |
| 坐席工作台 | 不需要 | 必需（收件箱、会话指派） |
| 会话状态机 | 简单（一问一答） | 复杂（机器人和人工来回切换） |
| 语气 | 中性、专业 | 友好、品牌化 |
| 答错代价 | 员工操作出错 | 客户流失、投诉、品牌受损 |

底层虽然都是 RAG，但对内系统八成精力花在检索质量和权限上，对外系统一大半精力花在坐席协作和状态机上。

---

## 2. 为什么不建议一套通吃

常有人想：做一套知识库，员工内部用，同时接上对外客服，岂不省事？

实际结果往往是两头都做不深。对内需要的细粒度权限（按角色、部门过滤文档），对外几乎用不上；对外需要的转人工、Copilot、坐席台，对内全是负担。两者的会话模型也完全不同，对内是无状态的问答，对外是有状态的多方会话。

硬塞进一套系统，架构会被两种需求来回拉扯，最后哪边都不好用。先把一种做透，另一种真需要时再单独做。

---

## 3. 两者共享的部分：检索内核

产品形态差得远，但有一块可以通用：

```
文档 → 分块 → embedding → 向量库 → 混合检索 → rerank
```

把文档变成可检索片段的这条内核，对内对外完全一样，区别只在它上面那一层：

```
          ┌─────────────────────┐
对内 →     │  权限过滤 + 直接问答    │
          ├─────────────────────┤
          │   共享检索内核         │  ← 本手册 05-07 章
          ├─────────────────────┤
对外 →     │  转人工 + 坐席协作      │
          └─────────────────────┘
```

所以跟着本手册把检索内核做扎实之后，将来要做对外客服，内核可以直接拿过去，在上面接交接逻辑就行。

---

## 4. 为什么选对内当教学载体

| 理由 | 说明 |
|------|------|
| 权限有独特价值 | 能不能做好权限，区分了真系统和 demo，最值得讲 |
| 主线干净 | 没有转人工和坐席台，RAG 主线不会被冲淡 |
| 可量化 | 答得准不准、引用对不对，都能打分 |
| 自包含 | 不用真上线，也不需要外部访客，跟着做的门槛低 |

对外客服的人机交接状态机也很有意思，但它会把手册的重心从 RAG 上拉走，更适合单独写。

---

## 5. 常见坑

| 坑 | 后果 | 正确做法 |
|----|------|----------|
| 对内系统硬加转人工 | 复杂度暴涨，又用不上 | 对内聚焦问答和权限 |
| 对外系统忽视权限 | 对外其实更要防数据泄漏，只是粒度不同 | 对外用「文档是否对外公开」一个开关就够 |
| 想一套通吃 | 两头都做不深 | 先做透一种 |
| 检索内核也分两套 | 重复造轮子 | 内核共享，只分上层 |
