# EKB 08：边界与非目标

> 一个项目能不能讲透，很大程度上取决于肯不肯做减法。这篇列出我们刻意不做的事，每一项都给出理由。边界划清楚了，有限的篇幅才能留给真正难的部分。

---

## 1. 为什么要先定非目标

需求会不停膨胀。「既然做了知识库，要不要再加个……」这类想法一旦放任，项目永远做不完，手册也讲不清。

所以先列一张非目标清单。新需求来了先对照这张表：在表里的直接拒绝，不在表里的再评估。

---

## 2. 我们不做的，以及为什么

| 非目标 | 为什么不做 |
|--------|-----------|
| 对外客服 / 转人工 / 坐席台 | 重心在人机交接，会冲淡 RAG 主线（见[对内知识库与对外客服的差别](02-internal-vs-external.md)） |
| 多轮对话记忆 | 知识库以单轮问答为主；多轮记忆是 07 手册的主题，这里不重复 |
| Agent 自主调工具 | 「查订单」这类 agentic 能力属于另一种场景，本项目只做检索问答 |
| 文档自动生成/写作 | 知识库是读文档，不是写文档 |
| 生产级高可用/扩缩容 | 教学项目，目标是讲清决策，不是扛百万 QPS |
| 多语言 | 聚焦中文；多语言只在 embedding 选型里作为一个变量提一下 |
| 花哨的前端 | 前端只做到能用、能演示流式和引用，不做设计稿级 UI |

---

## 3. 有几件事看着能砍，其实不能

做减法不等于什么都能砍。下面几项属于核心：

| 看着可砍 | 为什么必须做 |
|----------|-------------|
| 评估测试集 | 整个项目的标尺，没有它就是闭着眼改代码 |
| 权限过滤 | 对内知识库的核心价值，砍了就只剩个 demo |
| 引用溯源 | 没有引用的答案没人敢信 |
| 答不出时兜底 | 编答案在企业场景里是事故 |

能砍的是锦上添花的功能，地基不能动。设计阶段要能分清哪些是哪些。

---

## 4. 边界要有弹性：给将来留接口

不做不等于堵死。比较好的边界是现在不做，但也不挡将来的路：

- 不做对外客服，但检索内核是独立的，将来接坐席层可以直接复用。
- 不做多轮记忆，但 API 预留了 `session_id`，将来加对话历史不用改数据模型。
- 不做 Agent 工具，但生成层用的是 Pydantic AI，以后要挂工具直接就能挂。

这样既不过度设计，也不会把自己锁死。

---

## 5. 用一张图固定边界

```
            ┌──────────────────────────────┐
   做  →     │  对内问答 · 权限 · 引用 · 兜底   │  ← 本手册全部精力
            │  评估 · 检索增强 · 增量更新       │
            └──────────────────────────────┘
            ┌──────────────────────────────┐
 留口子 →    │  session_id · 独立检索内核       │  ← 设计上不挡路
            └──────────────────────────────┘
            ┌──────────────────────────────┐
  不做 →     │  转人工 · 坐席台 · Agent 工具     │  ← 明确拒绝
            │  多轮记忆 · 文档生成 · 高可用      │
            └──────────────────────────────┘
```

---

## 6. 常见坑

| 坑 | 后果 | 正确做法 |
|----|------|----------|
| 不定非目标 | 需求无限膨胀，做不完 | 先列非目标清单，新需求先对照 |
| 把地基也砍了 | 系统只剩个 demo | 分清锦上添花和地基 |
| 边界堵死，没留接口 | 将来扩展要推翻重来 | 不做但不挡路（留 session_id 等） |
| 接口留得太多 | 为「将来可能」过度设计 | 只留成本低、明显会用到的接口 |
