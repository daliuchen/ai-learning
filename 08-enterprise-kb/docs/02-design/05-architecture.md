# EKB 10：整体架构、数据流与组件职责

> 这篇把前几篇的需求、约束和数据模型拼成一张完整的架构图。系统里有两条数据流，离线的 Ingest 和在线的 Query，下面逐一说明它们经过哪些组件、每个组件做什么。后面各章都可以拿这张图当地图。

---

## 1. 全景架构

```
┌─────────────────────────────────────────────────────┐
│  前端 (Next.js / TS)                                   │
│  ├─ 问答页：输入 → SSE 流式答案 → 引用卡片               │
│  └─ 文档后台：上传 / 设可见角色 / 下线                   │
└──────────────────────┬──────────────────────────────┘
                       │ HTTP（提问/管理） · SSE（流式答案）
┌──────────────────────▼──────────────────────────────┐
│  AI 服务 (FastAPI / Python)                            │
│                                                       │
│  ┌─── Ingest 流（离线）────────────────────────────┐   │
│  │ parse → chunk → embed → upsert(chunks, acl)    │   │
│  └────────────────────────────────────────────────┘   │
│                                                       │
│  ┌─── Query 流（在线）─────────────────────────────┐   │
│  │ rewrite → ACL 过滤 → 混合检索 → rerank          │   │
│  │ → 裁剪 → Pydantic AI 生成（答案+引用+found）     │   │
│  └────────────────────────────────────────────────┘   │
└──────────────────────┬──────────────────────────────┘
                       ▼
              Postgres + pgvector
   documents · chunks · acl · eval_cases · query_logs
```

Ingest 在离线时把文档变成可检索的片段，Query 在线上把问题变成带引用的答案。两条流共用一个数据库，但触发时机和频率完全不同。

---

## 2. Ingest 流（离线，文档变更时触发）

```
文档（md/html）
  │ parse        解析成纯文本 + 结构（标题层级）
  ▼
原始文本 + 结构
  │ chunk        按语义/小节切片，每片带 section_path
  ▼
chunks（带元数据）
  │ embed        每片生成向量
  ▼
向量 + 文本
  │ upsert       写入 chunks 表（含 tsv），写 acl 表
  ▼
Postgres
```

这条流不在用户请求路径上，慢一点、批量处理都没关系。文档更新时增量重跑，详见[增量更新](../05-ingest/06-incremental.md)。

---

## 3. Query 流（在线，每次提问触发）

```
问题 + 用户角色
  │ rewrite       口语 → 接近文档表述的 query（07章）
  ▼
改写后的 query
  │ ACL 过滤      只在该角色可见的 doc 范围内检索（08章）
  ▼
候选 doc 集合
  │ 混合检索       BM25 + 向量，各召回 N 条（07章）
  ▼
召回的 chunks（含噪声）
  │ rerank        精排，选 top-k（07章）
  ▼
top-k chunks
  │ 裁剪          按 token 预算裁，拼进 prompt（07章/07手册）
  ▼
prompt
  │ generate      Pydantic AI → {答案, 引用, found}（06章）
  ▼
结构化答案 → SSE 流式返回前端 + 写 query_logs
```

这条流在用户请求路径上，对延迟敏感，每一步都要算时间预算，详见[成本与延迟预算](../10-production/02-cost-latency.md)。

## 4. 组件职责清单

| 组件 | 职责 | 章节 |
|------|------|------|
| parse | 文档 → 纯文本 + 结构 | 05 |
| chunk | 文本 → 带元数据的片段 | 05 |
| embed | 片段 → 向量（可切换模型） | 03/05 |
| rewrite | 口语问题 → 便于检索的 query | 07 |
| ACL filter | 按角色限定可检索范围 | 08 |
| hybrid retrieve | BM25 + 向量两路召回 | 07 |
| rerank | 召回结果精排 | 07 |
| generate | 拼 prompt → 结构化答案 | 06 |
| eval | 离线给检索和答案打分 | 04 |

每个组件都能单独测试、单独替换。自己写一层薄代码，相比用 LangChain 这种黑盒，最大的好处就在这里。

---

## 5. 为什么这样分层

| 设计 | 好处 |
|------|------|
| Ingest / Query 两流分离 | 离线的慢任务不拖累在线延迟 |
| 检索内核独立于生成 | 检索可以单独评估、单独优化 |
| ACL 作为独立的过滤步骤 | 权限逻辑集中在一处 |
| 生成层用结构化输出 | 引用和兜底由类型保证，不靠 prompt 碰运气 |
| 共用一个 Postgres | ACL 能和检索 join，少一个组件 |

---

## 6. 常见坑

| 坑 | 后果 | 正确做法 |
|----|------|----------|
| Ingest 和 Query 混在一条流里 | 文档处理拖慢问答 | 离线和在线分开 |
| ACL 过滤放在检索之后 | 越权文档先进了候选集才被滤掉，有泄漏风险 | 把过滤前置到检索范围上 |
| 检索和生成耦合 | 无法单独评估检索质量 | 分层，让检索能独立打分 |
| 没有统一的架构图 | 各章代码拼不起来 | 用本篇的图当地图 |
