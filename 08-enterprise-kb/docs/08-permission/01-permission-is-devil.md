# EKB 38：为什么权限是企业知识库的难点

> 不管权限的 RAG demo 谁都能做，能保证 HR 薪资文档绝不会被普通员工检索到的系统，才算企业知识库。权限没法事后补上，它要贯穿数据模型和检索流程。这篇讲权限为什么难做，以及在哪些地方做错会造成泄漏。

---

## 1. 权限是企业知识库的分水岭

```
玩具 RAG demo：所有文档对所有人可见 → 检索全库 → 答
企业知识库：    HR 文档只 HR 看、法务文档只法务看、未发布产品只产品组看
              → 必须按提问者身份限定可检索范围
```

没有权限控制，知识库就不能上线。把薪资细则、绩效标准、未发布的规划答给所有人，就是一次数据事故。所以权限是企业知识库的准入门槛，不是锦上添花。

---

## 2. 泄漏的四个入口

权限难做，是因为泄漏点很隐蔽，而且不止一处：

| 泄漏入口 | 怎么漏 |
|----------|--------|
| 检索召回 | 无权文档进了候选集，即使没展示，也进了 prompt |
| Prompt 拼接 | 召回时过滤了，日志或缓存里却留了全量 |
| 引用展示 | 答案过滤了，引用列表却露出了无权文档的标题 |
| 模型记忆/串话 | 多租户共用 context，A 的内容串到了 B |

最隐蔽的是第一个。很多人以为答案里没提到就不算泄漏，可只要无权文档进了 prompt，模型就可能在答案里复述它的内容，哪怕引用列表里没有它。所以过滤必须放在召回阶段，放在展示阶段就晚了。

---

## 3. 原则：在检索阶段过滤

```
❌ 错误（晚过滤）：
检索全库 → 召回含无权文档 → 喂给模型 → 答案/引用里再过滤掉无权的
   问题：无权内容已进 prompt，可能被复述；日志也记了

✅ 正确（早过滤）：
按角色限定范围 → 只召回有权文档 → 无权文档从未进入候选
   保证：模型根本看不到无权内容
```

这一章最要紧的就是这条：无权文档从一开始就不该进候选集，进了再藏已经晚了。具体做法见 [检索阶段过滤](./03-filter-at-retrieval.md)。

---

## 4. 权限模型要做多复杂

按需求选最简单、够用的模型，别过度设计：

| 模型 | 表达力 | 适合 |
|------|--------|------|
| 公开/不公开（单 flag） | 最弱 | 对外客服 |
| 基于角色（RBAC） | 中 | 大多数企业知识库（本项目采用） |
| 基于属性（ABAC） | 强 | 复杂合规场景 |
| 行级/字段级 | 最强 | 极敏感数据 |

本项目用 RBAC：员工有角色（engineer、hr、finance 等），文档标注可见角色，两边对上就可见。它足够覆盖「HR 文档只给 HR 看」这类需求，又不像 ABAC 那么复杂。第 02 章数据模型里的 `acl(doc_id, role)` 就是按这个思路设计的。

---

## 5. 权限和检索质量之间的拉扯

加了权限过滤，检索范围就会缩小，带来一个副作用：

```
普通员工提问 → 范围缩小到「公开文档」→ 候选变少
→ 如果某问题的答案在受限文档里 → 该员工就是查不到（这是对的！）
→ 但要确保：是「无权」而非「检索 bug」导致的查不到
```

所以权限上线后，评估要分清两种查不到：一种是无权，结果正确，应该走兜底；另一种是检索失败，属于 bug，要修。这也是评估用例要标 `asker_role` 的原因（见 [构建评估测试集](../04-eval/02-build-testset.md)），同一个问题换个角色，期望结果就不一样。

---

## 6. 常见坑

| 坑 | 后果 | 正确做法 |
|----|------|----------|
| 把权限当成事后功能 | 数据模型推翻重做 | 设计阶段就考虑进去 |
| 检索后或展示时才过滤 | 无权内容进了 prompt，可能被复述 | 召回阶段过滤 |
| 只过滤答案，不过滤引用 | 引用露出无权文档的标题 | 引用也按权限过滤 |
| 权限模型设计过度 | 复杂、难维护 | RBAC 够用就别上 ABAC |
| 不区分「无权」和「检索失败」 | 把漏洞当 bug，或反过来 | 评估用例标 asker_role |
