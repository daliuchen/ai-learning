# EKB 47：用 Prompt Caching 降低成本

> 知识库问答的 prompt 里，系统提示和高频文档片段会反复出现。用 prompt caching 把这些固定前缀缓存起来，重复请求只为变化的部分付费，成本和延迟都能明显下降。这篇讲 prompt 该怎么组织，才能尽量命中缓存。

---

## 1. 哪些部分能缓存

一次问答的 prompt 大致由四段组成：

```
[系统提示]        ← 每次都一样，可缓存
[（可选）高频文档]  ← 热门问题命中相同片段，部分可缓存
[检索到的片段]     ← 随问题变，不可缓存
[用户问题]         ← 每次都变，不可缓存
```

prompt caching 的原理是相同的前缀只算一次，之后命中缓存的请求跳过这部分的计算和计费。所以要把固定不变的内容放在 prompt 最前面（参见 [07 手册的 prompt caching](/docs/07-context-engineering/07-long-context/03-prompt-caching)）。

---

## 2. 让前缀保持稳定

```python
# ❌ 固定内容散在中间，缓存命中率低
prompt = f"{retrieved_chunks}\n\n规则：只用文档回答...\n问题：{q}"

# ✅ 固定前缀在最前，变化的在后
SYSTEM = "你是企业知识库助手。只能基于文档片段回答..."   # 长且固定 → 缓存
prompt = f"{retrieved_chunks}\n\n问题：{q}"               # 变化部分在后；SYSTEM 作为 instructions 传给 Agent，排在最前
```

各家触发缓存的方式不一样。Anthropic 的 Claude 要用 `cache_control` 显式标记缓存断点，或者在请求顶层开启自动缓存，什么都不设就不会缓存；OpenAI 按前缀匹配自动缓存，不需要标记；千问（百炼）有隐式缓存，也支持显式缓存；Gemini 的隐式缓存自动生效，显式缓存要先创建 cache 对象。思路都一样：让不变的内容成为稳定的前缀。系统提示越长、越固定，缓存的收益越大。

缓存还有最小长度。Claude Opus 5.5、Sonnet 5.5、Haiku 5.5 的可缓存前缀至少 512 token（更早的模型是 1024 到 4096 token，Bedrock 上以 AWS 文档为准），短于这个长度不会报错，只是 usage 里缓存写入和读取都是 0。系统提示只有几百 token 时，要把改写器指令、固定的格式示例等也放进同一段前缀，才凑得够长。

用 Pydantic AI（2.x）时不必手写 `cache_control`，在 `model_settings` 里打开即可：

```python
from pydantic_ai import Agent
from pydantic_ai.models.anthropic import AnthropicModelSettings

answer_agent = Agent(
    "anthropic:claude-sonnet-5-5",
    output_type=Answer,
    instructions=SYSTEM,                                   # 长且固定的系统提示
    model_settings=AnthropicModelSettings(
        anthropic_cache_instructions=True,                 # 缓存系统提示（也可写 '5m' / '1h' 指定 TTL）
    ),
)
# 想缓存更多：anthropic_cache='1h'（自动缓存到最后一个可缓存块）；
# 或在用户消息里放 CachePoint() 标记「这之前的内容都缓存」。一次请求最多 4 个缓存点。
```

要确认是否命中，看 `result.response.usage.cache_write_tokens`（首次写入）和 `cache_read_tokens`（后续命中）。千问默认走隐式缓存，想让命中更确定可以改用显式缓存，具体写法以百炼文档为准。

## 3. 知识库场景里能缓存什么

| 可缓存对象 | 怎么命中缓存 | 收益 |
|-----------|-----------|------|
| 系统提示 | 始终放最前、内容固定 | 每次请求省下系统提示的 token |
| 高频文档全文 | 极小的知识库可以全量缓存（见下） | 跳过 RAG |
| 改写器的系统提示 | query 改写器的指令固定 | 改写调用降本 |

检索到的片段每次都不一样，通常缓存不了，这是 RAG 和全量长上下文的区别。RAG 能缓存的主要是系统提示和改写器指令，单次省得不多，但 QPS 一高，累积起来就可观了。

---

## 4. 小知识库的特例：用全量缓存替代检索

如果知识库非常小（[第 12 篇](../03-selection/02-vector-db-pgvector.md) 提到过），可以反过来做：不检索，把全部文档放进可缓存的前缀里。

```
[系统提示 + 全部文档]   ← 一次性缓存住（几万 token）
[用户问题]              ← 每次只付问题的 token
```

前提有两条：一是文档总量要明显小于模型的上下文窗口，给指令、对话历史和输出留足余量，而且文档越长，每次请求要付的缓存读取费用越多，模型在长上下文里也更容易漏看信息，最好先用评测集比一比全量放入和 RAG 的答案质量；二是文档不常更新，因为一更新缓存就失效。满足这两条，连向量库都可以省掉。不过企业知识库通常超出这个量级，所以本项目的主线仍是 RAG 加系统提示缓存。两种做法该选哪个，取决于知识库的规模。

---

## 5. 缓存会失效

缓存不是永久有效的，有三种情况会让它失效：

- TTL 到期：缓存有生存时间（比如 5 分钟），请求频率低的话可能每次都 miss
- 前缀变了：系统提示哪怕只改一个字，整段缓存都失效，所以别频繁改 prompt
- 文档更新：如果缓存了文档全文，文档一改缓存就失效

我的建议是先把系统提示定下来，别动不动就改措辞，命中率自然就高。在频繁 A/B 测试 prompt 的阶段，缓存收益会打折扣，这是评估迭代期正常要付的代价。

---

## 6. 常见坑

| 坑 | 后果 | 正确做法 |
|----|------|----------|
| 固定内容放在 prompt 中间 | 缓存命中率低 | 不变的内容放最前 |
| 频繁改系统提示 | 缓存反复失效 | prompt 稳定后再上缓存 |
| 指望检索片段也能缓存 | 片段每次都变，缓存不了 | 以缓存系统提示为主 |
| 小知识库还硬走 RAG | 错过全量缓存这种更简单的做法 | 按规模判断 |
| 不监控缓存命中率 | 不知道到底省了多少 | 观测缓存命中（见[可观测性](04-observability.md)） |
