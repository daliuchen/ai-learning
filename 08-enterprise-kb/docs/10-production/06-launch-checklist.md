# EKB 52：上线 Checklist

> 功能齐全、能跑通，离敢上线还有一段距离。这篇给出一份上线检查清单，覆盖质量、安全、性能、运维、反馈五个方面，逐条通过才发布。我把它当成门禁来用，安全红线尤其如此，有一条没过就不上线。这也是整本手册的最后一篇。

---

## 1. 质量门禁

指标达标才能发布，标准来自评估集（见 [评估先行](../04-eval/01-why-eval-first.md)）：

- [ ] recall@5 ≥ 目标值（如 0.80）
- [ ] 引用准确率 ≥ 目标值（如 0.85）
- [ ] 兜底正确率 ≥ 0.95（答不出时不编，权重最高）
- [ ] 各类问题（直球、口语、专名、跨文档）分别达标，不被平均分掩盖
- [ ] 评估集覆盖了主要的文档空间和角色

```python
def quality_gate(rows):
    assert recall_at_5(rows) >= 0.80
    assert citation_accuracy(rows) >= 0.85
    assert fallback_accuracy(rows) >= 0.95     # 不编答案
    print("✅ 质量门禁通过")
```

---

## 2. 安全红线：一条不过就不上线

下面这些没有商量余地：

- [ ] 越权召回 = 0：`leak_scan` 穷举扫描全部通过（[第 42 篇](../08-permission/05-no-leak-verify.md)）
- [ ] 引用层不泄漏受限文档
- [ ] 角色来自服务端的可信来源，前端无法伪造
- [ ] BM25 和向量两路都验证过权限
- [ ] 多角色用户、修改可见性这些场景都测过
- [ ] 日志和 trace 不泄漏受限内容

```python
def security_gate(conn):
    assert leak_scan(conn) == [], "越权泄漏，禁止上线！"
    # 红线：不通过直接 fail，不存在「先上线再修」
```

质量可以上线后慢慢改进，安全红线不行，越权泄漏一次就是事故。

---

## 3. 性能门禁

- [ ] TTFT P95 < 目标（如 1.5s）
- [ ] 总延迟 P95 < 目标（如 4s）
- [ ] 单次问答成本 < 预算（如 $0.01）
- [ ] prompt caching 命中率达标
- [ ] 按预期并发做过压测

---

## 4. 运维就绪

- [ ] 可观测已接好，能回放任意一次问答的完整链路（[第 50 篇](./04-observability.md)）
- [ ] 核心指标有监控面板（found 率、延迟、成本、「没用」反馈率、越权数）
- [ ] 越权召回数有实时告警
- [ ] 文档增量更新流程跑通（[第 26 篇](../05-ingest/06-incremental.md)）
- [ ] 数据库有备份，向量索引可以重建
- [ ] 模型 API 失败时有降级方案（超时、限流时的 fallback）

---

## 5. 反馈机制就绪

- [ ] 反馈入口已上线（有用、没用、引用不准）
- [ ] `query_logs` 记录完整
- [ ] 定好复盘节奏（每周看趋势，每月重新评估）
- [ ] 从日志里捞评估用例的流程已跑通（[第 49 篇](./03-feedback-loop.md)）

## 6. 把门禁接进 CI

上面这些门禁不是上线前手动跑一次就算了，而要在每次改动时自动跑，防止回归：

```python
# CI: 任何 PR 合并前必跑
def launch_gate(conn):
    rows = run_eval()
    quality_gate(rows)        # 质量达标
    security_gate(conn)       # 安全红线（最重要）
    perf_gate()               # 性能达标
    print("✅ 全部门禁通过，可发布")
```

安全门禁更要常驻 CI。重构检索、改缓存、调融合参数，都可能在不经意间破坏权限。门禁没过，就不允许合并。

## 7. 回顾整本手册

这本手册把前 7 本讲过的零件拼成了一个完整的系统，各章顺序如下：

```
选型方法论（不追最强，匹配规模）
→ 评估先行（立标尺，不闭眼改）
→ Ingest（语义分块带元数据）
→ 基础 RAG（结构化输出 + 引用 + 兜底）
→ 检索增强（混合 + rerank + 改写，每步量化）
→ 权限（检索阶段过滤，越权零泄漏）
→ 前端（流式 + 引用回链 + TS/Python 拆分）
→ 生产化（降本、可观测、排障、门禁）
```

各章反复用到的做法有四条：先定边界再选型；每次改动都用评估集量化；权限在检索阶段过滤；上线后收集用户反馈，把差评问题补进评估集。

---

## 8. 常见坑

| 坑 | 后果 | 正确做法 |
|----|------|----------|
| 能跑就上线 | 质量和安全都没保障 | 五个方面的门禁都过一遍 |
| 安全问题「先上线后修」 | 一泄漏就是事故 | 红线不过不上线 |
| 门禁只在上线前跑一次 | 后续改动可能破坏 | 接进 CI 常驻 |
| 没有反馈机制就上线 | 哪些问题没答好无从知道，系统停在上线时的水平 | 反馈入口和日志先就位 |
| 只看平均指标 | 薄弱环节被掩盖 | 分类型查看，红线单独查 |
