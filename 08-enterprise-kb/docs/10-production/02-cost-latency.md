# EKB 48：成本与延迟预算

> 上线之前，要给单次问答算两笔账：花多少钱，花多长时间。把成本和延迟拆到 embed、检索、rerank、改写、生成每个环节上，就能看清钱和时间都花在哪、哪里还能省。这篇给出预算模型和对应的优化手段。

---

## 1. 单次问答的延迟拆解

先把 Query 流每一步的耗时列出来（示意值）：

```
query 改写（小模型）   ~300ms   ← 一次额外模型调用
embed query           ~30ms
向量检索（pgvector）   ~20ms
BM25 检索             ~15ms
rerank（20候选）       ~150ms   ← cross-encoder
生成（流式，到首字）    ~500ms   ← TTFT，用户感知的「快慢」
─────────────────────────────
首字延迟（TTFT）       ~1秒
```

用户感受到的快慢取决于首字延迟（TTFT），而不是总时长。流式输出时，答案一开始往外蹦字，用户就觉得快了。所以优化的重点是让第一个字尽早出现。改写和 rerank 都卡在生成之前，是 TTFT 里的大头。

---

## 2. 延迟优化手段

| 手段 | 省哪里 | 代价 |
|------|--------|------|
| 改写用小模型/可跳过 | 省 ~300ms | 简单问题跳过改写 |
| rerank 候选数调小 | 省 rerank 时间 | 召回窗口变窄 |
| 并行化检索 | 向量/BM25 并行而非串行 | 实现复杂度 |
| 缓存高频问题的答案 | 省整条链 | 答案时效（文档更新要失效）|
| 流式 | 改善 TTFT 体感 | 已默认 |

性价比最高的两项是：简单问题跳过改写，能省约 300ms；热门问题的答案做缓存，命中就直接返回。后者要记得在文档更新时让缓存失效。

---

## 3. 单次问答的成本拆解

按 token 计价（示意。价格随模型和时间变化，请到各厂商官方定价页查当前价格，千问以百炼控制台「模型广场」为准）：

```
query 改写（小模型）  输入~50 + 输出~50 token    小模型单价低，占比很小
生成（强模型）        输入 = 系统提示 + 4个片段 ≈ 2000 token
                     输出 ≈ 200 token
─────────────────────────────────────────
主要成本在「生成」的输入 token（片段占大头）
```

按 Sonnet 5.5 的标价（输入 $2、输出 $10 每百万 token）算，生成这一步约 2000 × $2/M + 200 × $10/M ≈ $0.006，第 5 节「单次问答 < $0.01」的预算就是这么来的。

成本主要花在生成环节的输入 token 上，其中检索片段占得最多。所以省钱可以从这几处下手：

- 少塞片段：rerank 之后只取真正相关的 3 到 4 条，片段多了不光贵，噪声还会拉低准确率
- 缓存系统提示，也就是上一篇的 prompt caching
- 改写、兜底这类非核心环节用小模型
- 对片段去重、裁剪，把重叠内容和过长的片段砍掉（见 [07 手册的裁剪](/docs/07-context-engineering/03-retrieval/04-rank-trim)）

---

## 4. 强模型和小模型的分工

不是每个环节都需要强模型，按重要性分配：

| 环节 | 模型档位 | 理由 |
|------|----------|------|
| 生成答案 | 强（当前主力档，如 Claude Sonnet 档 / GPT 主力档 / `qwen-plus` 档） | 忠于文档、不编造，需要较强的指令遵循 |
| query 改写 | 小（Haiku / `qwen-flash` 这一档） | 改写任务简单，小模型够用 |
| 兜底判断 | 随生成 | 已在生成里完成 |
| 评估 judge | 中~强 | 判断要准 |

生成决定答案质量，用强模型；改写只是辅助，用小模型就够了。生成本来就占了成本的大头，改写也换成强模型时总成本涨得不算多，但每次请求都多付一次强模型的费用和延迟，改写质量却提升有限。

---

## 5. 定预算目标，持续监控

预算算完不能就放着，要定目标，并持续监控：

```
目标（示例）：
  TTFT < 1.5s（P95）
  单次问答成本 < $0.01
  总延迟 < 4s（P95）

监控（下章可观测）：
  每次问答记录各环节耗时 + token 用量 → 看 P50/P95
  超标告警
```

预算一旦超标，就回到上面的拆解表，看是哪个环节涨了：rerank 候选给多了，还是片段塞多了。拆解做得细，排查时才有方向。

---

## 6. 常见坑

| 坑 | 后果 | 正确做法 |
|----|------|----------|
| 只看总延迟 | 忽略了用户真正感受到的 TTFT | 优化首字延迟 |
| 所有环节都用强模型 | 改写这类简单环节多花钱、多加延迟，收益很小 | 按重要性分配模型档位 |
| 片段塞得太多 | 又贵，噪声还拉低准确率 | rerank 后只取精 |
| 不设预算目标 | 上线后成本失控 | 定目标并监控 |
| 答案缓存不失效 | 文档更新后还答旧内容 | 缓存绑定文档版本 |
