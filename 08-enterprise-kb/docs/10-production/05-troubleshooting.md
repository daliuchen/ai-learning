# EKB 51：RAG 常见故障排查

> 用户反馈「答得不对」时，原因可能在检索、生成、数据或权限任何一层。这篇给出一套排查思路：从症状出发，借助 trace 一层层往下查，定位到具体是哪一层，再给出对应的修法。前面各章讲过的内容，在这里会串起来用一遍。

---

## 1. 第一步：判断是哪一层

RAG 出错时，先用 trace 把问题归到某一层，思路和评估的分层一致：

```
症状：答得不对
  │
  ├─ 看 trace：相关文档在召回结果里吗？
  │   ├─ 不在 → 【检索层问题】
  │   └─ 在 → 看 rerank 排序
  │        ├─ 排得很后/被裁掉 → 【排序问题】
  │        └─ 进了 prompt → 【生成层问题】
  │
  └─ trace 显示 found=false 但其实库里有 → 【阈值/检索问题】
```

先定位到层，再动手修。别一上来就调 prompt，问题很可能出在检索没召回。

---

## 2. 症状、病因、修法对照表

| 症状 | 可能病因 | 怎么确认 | 修法 |
|------|----------|----------|------|
| 该有的答案答不出 | 检索没召回 | 在 trace 里看召回结果有没有目标 doc | 加改写、混合检索，或调 chunk |
| 答案张冠李戴 | 召回了无关片段且排在前面 | 看 rerank 分数 | 调 rerank / 收紧阈值 |
| 模型编了个答案 | 兜底失守 | 看 found 和片段相关度 | 强化三道防线（[第 30 篇](../06-basic-rag/04-say-i-dont-know.md)） |
| 引用指向错误文档 | rerank 排序或分块有问题 | 对比 cited 和实际相关的文档 | 调 rerank / 重新分块 |
| 答案不全 | 片段被切断或召回不全 | 看 chunk 边界 | 调分块大小和重叠 |
| 专有名词查不到 | 向量对专名不敏感 | 看 BM25 那一路有没有命中 | 确认 BM25 + 专名词典 |
| 口语问题查不到 | 表述差得太远 | 看改写是否生效 | 检查 query 改写 |
| 越权看到文档 | 权限过滤有漏洞 | leak_scan | 修过滤（[第 40 篇](../08-permission/03-filter-at-retrieval.md)） |
| 延迟突然变高 | 某个环节退化 | 看各步 latency | 找出变慢的环节 |

## 3. 检索层问题再细分

如果确定是检索没召回，继续往下拆：

```
召回不到目标文档？
  ├─ 文档真的 ingest 了吗？      → 查 chunks 表有没有这文档的 chunk
  ├─ embedding 是不是坏了？      → 查向量是不是全 0 / 维度对不对
  ├─ 是不是被权限过滤掉了？      → 用 all 角色重试，看是不是权限问题
  ├─ 是专名/口语错配吗？         → 看 BM25 和改写有没有兜住
  └─ 知识库里压根没有？          → 这不是 bug，该走兜底 / 补文档
```

最后一种情况最容易被当成 bug。库里本来就没有的内容，检索再强也召回不到。所以先确认数据存在，再去怀疑检索。

---

## 4. 生成层问题再细分

如果片段是对的，答案却歪了：

```
片段进了 prompt 但答案不对？
  ├─ 片段里真的有答案吗？        → 人读一遍片段，确认信息在
  ├─ 模型忽略了片段用了常识？     → 强化系统提示「只用片段」
  ├─ 片段太多噪声淹没了？        → 减少 top-k，rerank 更狠
  ├─ prompt 拼接格式乱？         → 检查 format_chunks
  └─ 模型能力不够？             → 换更强模型试
```

## 5. 一个排查示例

```
报告：「问『飞书怎么改密码』答不出，但确实有《飞书使用指南》」

1. 看 trace → 召回结果里没有飞书指南 → 检索层问题
2. 查 chunks → 飞书指南的 chunk 存在 ✅，排除「没 ingest」
3. 用 all 角色重试 → 还是召回不到 → 排除权限
4. 看两路：向量召回排第 30，BM25 也很后
5. 发现：jieba 默认词典里「飞书」切法不稳定，问题「飞书怎么改密码」
   切成「飞」「书」，文档里「在飞书里提交审批」却切成「飞书里」
   → 两边的词对不上，BM25 匹不中
6. 修：jieba.add_word("飞书")，重建 BM25 索引
7. 重试 → 飞书指南召回到 top-3 ✅
8. 补一条评估用例防回归
```

这个例子走完了从症状到修复的全过程：看 trace，逐层排除，找到根因，修掉，最后补一条回归用例。每次排障都应该以补一条评估用例收尾，免得同样的问题再出现。

---

## 6. 常见坑

| 坑 | 后果 | 正确做法 |
|----|------|----------|
| 一出错就调 prompt | 问题可能根本在检索 | 先分层定位 |
| 把缺数据当 bug 修 | 白费功夫 | 先确认数据存在 |
| 修完不补回归用例 | 同样的问题反复出现 | 每次排障以补用例收尾 |
| 没有 trace，全靠猜 | 定位慢，还容易修错 | 依靠可观测 |
| 只修这一例，不看同类 | 同类问题还在 | 检查是否是一类问题 |
