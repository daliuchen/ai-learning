# EKB 49：反馈闭环

> 知识库上线只是开始。用户点的「有用」「没用」「引用不准」，加上 `query_logs` 里那些没答好的真实问题，都是后续优化最好的素材。这篇讲怎么收集反馈，怎么把它们变成评估用例和具体的改进动作，让上线、反馈、改进、再上线形成闭环。

---

## 1. 整体流程

```
用户提问 → 系统回答 → 用户反馈（👍/👎/引用不准）
   │                          │
   │                          ▼
   │                    写入 query_logs
   │                          │
   │         ┌────────────────┴────────────────┐
   │         ▼                                  ▼
   │   答不好的问题                        引用被标错的
   │         │                                  │
   │         ▼                                  ▼
   │   补进评估集 / 补文档                调检索/分块
   │         │                                  │
   └─────────┴──────── 改进后重新评估 ──────────┘
```

用户反馈和失败问题都写进 `query_logs`，按类型分诊之后，有的去补文档，有的变成评估用例，改完再用评估集验证一遍。

---

## 2. 收集哪些信号

| 信号 | 来源 | 说明什么 |
|------|------|----------|
| 有用/没用 | 用户点击 | 对答案整体是否满意 |
| 引用不准 | 引用卡片上的按钮（[第 44 篇](../09-frontend/02-citation-clickback.md)） | 检索或排序有问题 |
| 追问/重问 | query_logs 里同一个人连续问相似问题 | 上一次没答好 |
| found=false 率 | 系统记录 | 哪些问题知识库没覆盖 |
| 零反馈但低相关度 | 检索分数低 | 可能没答好 |

`query_logs` 表（[第 09 篇](../02-design/04-data-model.md)）已经存了问题、检索结果、答案、found 和 feedback，分诊需要的原料都在这些字段里。

---

## 3. 从反馈到行动：先分诊

不同信号对应不同的修法，不能混在一起处理：

```python
def triage_feedback(log_row) -> str:
    if not log_row["found"]:
        return "缺文档"          # 知识库没这内容 → 补文档
    if log_row["feedback"] == -1 and log_row["retrieved_ids"]:
        # 召回了但答不好 → 看是检索排序问题还是生成问题
        return "检索或生成"
    if log_row["bad_citation"]:   # 来自「引用不准」反馈（第 44 篇），query_logs 需加这一列或 join 反馈表
        return "检索排序"        # 引用错 → rerank/分块
    return "ok"
```

| 分诊结果 | 行动 |
|----------|------|
| 缺文档 | 通知文档负责人补充，再走 ingest |
| 检索排序 | 检查 rerank 和分块，把问题补进评估集再调 |
| 生成问题 | 检查 prompt，片段是对的但答歪了 |

先判断问题出在哪一层（检索、生成还是缺数据），再动手，这和评估的分层思路一致（见 [评估先行](../04-eval/01-why-eval-first.md)）。

---

## 4. 把真实问题补进评估集

反馈最有价值的用处，是用真实的失败案例扩充评估集：

```python
# 从日志里捞答不好的，人工核对后加进 testset
def harvest_eval_cases(conn):
    bad = conn.execute(
        "SELECT question, user_role, retrieved_ids, found "
        "FROM query_logs WHERE feedback = -1 "
        "ORDER BY created_at DESC LIMIT 50").fetchall()
    # 人工核对：这个问题正确答案在哪篇文档？标成新评估用例
    return bad
```

这样，评估集就从上线前凭经验想出来的 20 条，慢慢长成反映真实使用情况的几百条，越来越接近真实的问题分布。[第 18 篇](../04-eval/02-build-testset.md) 说评估集会跟着项目一起长，用户反馈就是它长大的主要来源。

---

## 5. 处理节奏

不需要实时处理，定期跑一遍就行：

```
每周：看 👎 率、found=false 率、bad_citation 率的趋势
每周：捞 top 失败问题，分诊 → 补文档 / 补评估用例
每月：用扩充后的评估集重新评估，看整体指标趋势
按需：指标下滑时，回到对应环节优化
```

---

## 6. 常见坑

| 坑 | 后果 | 正确做法 |
|----|------|----------|
| 没有反馈入口 | 不知道哪些问题没答好 | 提供有用/没用按钮和引用反馈 |
| 收集了但不分诊 | 不知道该修哪一层 | 先分诊再行动 |
| 不把真实问题补进评估集 | 评估集脱离实际 | 持续从日志里捞用例 |
| found=false 不跟进 | 知识盲区一直存在 | 通知相关人补文档 |
| 没有固定复盘节奏 | 反馈堆着没人处理 | 每周、每月固定复盘 |
