# EKB 32：为什么 RAG 的上限由检索决定

> RAG 由检索和生成两半组成，上限却是检索定的：该用的片段没被找回来，模型再强也只能答不出或者编。企业知识库里最常见的检索问题，是员工的口语和文档里的术语对不上。这一章在 MVP 的基础上逐项加增强（BM25、混合融合、rerank、query 改写），每加一项都用评估集量一次。

---

## 1. 检索漏了，生成补不回来

```
用户问「钱能不能要回来」
文档里写的是「退款流程」
向量检索：「钱」和「退款」语义相关，可能召回；但「要回来」是口语，召回排名靠后
→ 退款文档没进 top-5
→ 模型拿到的全是无关片段
→ 要么答不出，要么用其它片段瞎拼
```

这种情况怪不到模型头上。无论用哪家的模型，它都只能根据你喂给它的片段作答，片段错了，答案也不会对。所以优化 RAG 的顺序是先检索、后生成。

---

## 2. 企业知识库的三类检索错配

员工的问法和文档的写法，对不上的情况大致有三种：

| 错配类型 | 例子 | 哪种检索能救 |
|----------|------|--------------|
| 同义/口语 | 「钱要回来」vs「退款」 | query 改写 + 向量 |
| 专有名词/缩写 | 「OA 怎么登」，OA 是专名 | BM25 关键词 |
| 表述距离远 | 「新人第一天干啥」vs「入职流程」 | query 改写 |

单路向量检索处理同义词还算可以，但遇到专有名词和缩写经常失手（embedding 对罕见专名不敏感），口语化的问法也容易漏。所以后面要加混合检索和 query 改写。

---

## 3. 本章的增强路线

在 MVP 单路向量检索的基础上，按顺序加四项，每项单独评估。下图里的 recall 数字是示意数据，用来说明路线，不是实测结果：

```
MVP: 单路向量          recall@5 = 0.66 (baseline)
 │
 ├─ + BM25 关键词       → 专名/缩写召回改善
 ├─ + 混合融合（RRF）    → 两路优势结合
 ├─ + Rerank 精排       → 头部排序质量
 └─ + Query 改写        → 口语/远表述召回
                        recall@5 = ? （逐步逼近 0.85+）
```

每加一项都跑一次 `run_eval`，记下变化量。一次只加一项，这样才知道每一项各值多少，这是 [MVP 优先](../01-intro/04-mvp-first.md) 那篇立下的规矩。

---

## 4. 召回和精排是两件事

检索分两个阶段，目标正好相反：

```
召回阶段（recall 优先）：宁可多召回，别漏。k 设大（如 20）
   → BM25 + 向量两路，各召回 20 条，合并
精排阶段（precision 优先）：从召回里挑最相关的少数。
   → rerank 排序，取 top 3-5 进 prompt
```

新手常在召回阶段就只取 top-5，窗口太窄，相关片段排在第 7 位就被扔掉了。召回要宽（20 条），精排再收窄（5 条）。细节见 [Rerank 精排](./04-rerank.md)。

---

## 5. 检索质量的上下限

加增强之前，先弄清检索质量的边界在哪：

- 下限：检索再差，也有距离阈值兜底，不会拿一堆不相关的片段硬答。
- 上限：受分块质量和数据本身限制。文档里压根没写的知识，检索再强也找不回来，这时应该走兜底，或者提示去补文档。

所以别指望检索增强包治百病。评估时如果发现某些问题的 recall 一直是 0，先分清是检索不行，还是知识库里本来就没有。后者要回到 ingest 补文档，调检索没用。

---

## 6. 常见坑

| 坑 | 后果 | 正确做法 |
|----|------|----------|
| 只换大模型优化生成，不动检索 | 检索漏了，换模型也没用 | 先优化检索 |
| 召回阶段就取 top-5 | 相关片段早早被丢掉 | 召回宽、精排窄 |
| 一次加多项增强 | 说不清是哪项起的作用 | 一次一项，跑评估 |
| 什么问题都怪检索 | 实际是缺文档 | 区分「检索差」和「没数据」 |
| 不设距离阈值 | 不相关的片段进了生成 | 用阈值兜底 |
