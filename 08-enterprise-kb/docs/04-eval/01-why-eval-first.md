# EKB 17：评估先行，先立标尺再写检索

> 很多人习惯把评估放到最后，等功能做完再测。我的做法相反：评估是这个项目的第一段代码。没有标尺，后面每一次优化都只能凭感觉，改完到底变好还是变坏，说不清。

---

## 1. 没有评估，等于闭着眼开车

先看没有评估集时的迭代过程：

```
改了分块策略 → 跑几个问题 → 「感觉答得还行」→ 留下
加了 rerank   → 又跑几个   → 「好像更好了？」→ 留下
调了 prompt   → 再跑几个   → 「诶这个变差了？还是我记错了」→ ？？？
```

每一步都靠感觉和记忆判断，而这两样都不可靠。最基本的问题，「这次改动让系统好了多少」，你回答不上来。

有了评估集，过程变成下面这样（数字是示意数据，用来说明流程）：

```
baseline: recall@5 = 0.66, 引用准确率 = 0.70
加 BM25 混合 → recall@5 = 0.79 ✅ 涨了 0.13，留下
调 prompt → 引用准确率 = 0.68 ❌ 跌了，回退
```

每一步都有数字，留还是退一目了然。工程和玄学的分界就在这里，[04 手册](/docs/04-prompt-engineering/01-foundations/05-eval-first) 也反复讲过这一点。

---

## 2. 为什么要先做，而不是后补

「先做完功能再补评估」听起来顺理成章，但后补会带来几个问题：

| 后置评估的问题 | 前置评估的好处 |
|----------------|----------------|
| 做的时候没标尺，全凭感觉堆 | 每个增强都能验证是否真有用 |
| 做完才发现方向错了，返工 | 早期就发现「这条路不通」 |
| 评估集事后补，容易迎合现有实现 | 评估集独立于实现，更客观 |
| 选型（embedding/模型）没依据 | 用评估集做选型决策 |

评估集可以看成需求规格的可执行版本：它定义了什么叫答得好。先写它，目标就先钉死了。

---

## 3. 评估集在这个项目里要用很多次

它不只是最后打一次分，项目里好几个环节都靠它：

- 选 embedding（03 章）：哪个模型 recall 高
- 选生成模型（03 章）：哪个模型引用准、不乱编
- 验证每个检索增强（07 章）：BM25、rerank、改写各涨多少
- 验证权限（08 章）：越权文档是否真的不召回
- 上线前把关（10 章）：指标达标才发布
- 回归测试：改完代码跑一遍，确认没有退化

做一份，用到上线，所以值得排在最前面。

---

## 4. 评估分两层

RAG 出错可能出在检索，也可能出在生成，所以评估也分两层：

```
检索层评估：召回的片段对不对？
   指标：recall@k（该命中的文档有没有被检索到）
   ↓
生成层评估：基于片段的答案对不对？
   指标：引用准确率、答案正确性、兜底正确率
```

分层是为了定位。答案错了，你得知道是检索没召回对的片段，还是片段对了、模型答歪了。前者改检索，后者改 prompt 或换模型，修法完全不同。指标的细节见 [评估指标](./03-metrics.md)。

---

## 5. 第一版不必完美

有人觉得评估集很难建全，于是一直拖着不做。我的看法是先有 20 条，比什么都没有强得多。

```
第一版：20 条最典型的问题 + 期望文档，够你开始量化迭代
后续：从 query_logs 里发现答不好的真实问题，持续补进评估集
```

评估集会跟着项目一起长。眼下要的是一个能跑的版本，不必等一个完美的版本。怎么建见 [构建评估测试集](./02-build-testset.md)。

---

## 6. 常见坑

| 坑 | 后果 | 正确做法 |
|----|------|----------|
| 评估放最后 | 全程凭感觉，方向错了才发现 | 评估是第一段代码 |
| 只评估答案，不评估检索 | 答错了不知道是哪层的问题 | 分检索、生成两层评估 |
| 等评估集完美再开始 | 一直开始不了 | 先 20 条，后续持续补 |
| 评估集迎合现有实现 | 测不出真问题 | 评估集独立定义「什么叫好」 |
