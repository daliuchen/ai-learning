# EKB 18：构建评估测试集

> 评估集说穿了就是一组「问题 → 期望命中的文档（加上期望答案要点）」。这篇讲怎么从零造出第一版 20 条：该覆盖哪些题型，以及为什么每条都要标上提问人的角色。后面所有迭代都拿它当标尺。

---

## 1. 一条评估用例长什么样

最小结构是一个问题、它应该命中哪些文档，再加上可选的答案要点：

```jsonl
{"id": 1, "question": "年假有几天怎么申请？", "expected_doc_ids": [12], "asker_role": "all", "answer_points": ["按工龄1-5年5天", "OA系统提交"]}
{"id": 2, "question": "差旅报销单次上限多少？", "expected_doc_ids": [7, 9], "asker_role": "all", "answer_points": ["2000元", "15个工作日内"]}
{"id": 3, "question": "VPN连不上怎么办？", "expected_doc_ids": [21], "asker_role": "engineer", "answer_points": ["重启客户端", "联系IT"]}
{"id": 4, "question": "公司明年的薪资普调计划？", "expected_doc_ids": [], "asker_role": "all", "answer_points": ["应答：未找到"]}
```

文件放在 `eval/testset.jsonl`，一行一条。第 4 条的 `expected_doc_ids: []` 是故意留的「答不出」用例，用来验证兜底。

---

## 2. 要覆盖哪些题型

20 条要有代表性，我按下面的比例配：

| 类型 | 占比 | 作用 | 例子 |
|------|------|------|------|
| 直球问题 | ~40% | 基本检索能力 | 「年假几天」 |
| 口语/同义问法 | ~25% | 测 query 改写、混合检索 | 「钱能要回来吗」=退款 |
| 跨文档问题 | ~15% | 测多片段召回 | 答案散在两篇文档 |
| 答不出问题 | ~10% | 测兜底（不能编） | 知识库里没有的 |
| 权限相关 | ~10% | 测越权不召回 | 普通员工问薪资细则 |

口语问法和答不出这两类最容易漏掉，偏偏最能暴露问题。直球问题谁都能答对，拉不开差距。

---

## 3. 用例从哪来

有三个来源，难度依次递增。

### 人工照着文档造（起步）

翻一遍 demo 文档，每篇想一两个员工会怎么问，记下它应该命中哪篇。20 篇文档能出 20 到 40 条，起步最快。

### 让 LLM 帮忙生成（提速）

把一篇文档交给模型，让它反向出题：

```python
# 用 LLM 从文档反向生成问题
prompt = f"""这是一篇企业文档：
{doc_content}

请生成 3 个员工可能会问、且答案能在本文档找到的问题。
再生成 1 个口语化、用词和文档不同的问法。
输出 JSON 列表。"""
```

生成完要人工过一遍，把不合理的剔掉。这样比纯手写快不少。

### 真实日志（上线后，价值最高）

上线以后从 `query_logs` 里捞真实问题，尤其是用户点了「没用」的那些。它们暴露的正是系统的弱点，补进评估集最有用。做法见 [反馈闭环](../10-production/03-feedback-loop.md)。

## 4. 为什么要标 `asker_role`

原因是权限。同一个问题，换个角色来问，期望命中的文档就可能不一样：

```jsonl
{"question": "薪资是怎么核算的？", "asker_role": "hr", "expected_doc_ids": [30]}
{"question": "薪资是怎么核算的？", "asker_role": "engineer", "expected_doc_ids": []}
```

HR 问能命中薪资细则（doc 30）；普通工程师问应该什么都命中不到，因为没有权限，期望为空，系统应该走兜底。这一对用例直接验证了权限过滤是否生效。不标 `asker_role`，权限就没法评估。完整的越权验证见 [验证越权内容不会被召回](../08-permission/05-no-leak-verify.md)。

---

## 5. 造完自查一遍

20 条造完，对照下面几项检查：

- [ ] 有没有口语/同义问法？（不能全是直球）
- [ ] 有没有「答不出」用例？（验证兜底）
- [ ] 有没有权限用例？（同问题不同角色）
- [ ] `expected_doc_ids` 是不是真的核对过原文？（标错了评估就废了）
- [ ] 覆盖了主要文档空间（hr/it/product）吗？

第 4 项最要紧。期望文档标错了，整份评估就成了一把刻度错误的尺子，比没有还糟。

---

## 6. 常见坑

| 坑 | 后果 | 正确做法 |
|----|------|----------|
| 全是直球问题 | 拉不开差距，测不出改进 | 加口语、同义、跨文档题 |
| 没有答不出用例 | 兜底没法验证 | 留 ~10% 期望为空 |
| 不标 asker_role | 权限无法评估 | 每条标提问角色 |
| expected_doc_ids 没核对 | 标尺本身是错的 | 逐条核对原文 |
| 想一次造 200 条 | 迟迟开始不了 | 先 20 条，持续补 |
